Oracle Signal Handler Functions

2026/03/27

Signal handlers are programmer-defined functions that a process can register to respond to signals such as SIGINT, SIGTERM, or SIGSEGV.

When a signal is delivered, the operating system interrupts the normal execution flow and invokes the registered handler function, allowing the program to react and to clean up resources, log additional information, or terminate gracefully.

If no custom handler is registered, the system uses a default action, which in many cases means terminating the process or ignoring the signal.

I was interested in understanding which signal handlers Oracle processes use and how to identify the handler functions registered for each signal within an Oracle process. The following is a summary of this investigation.

To interpret the strace output, we need to understand the sigaction system call, which takes the following arguments (see also [1]):

The first argument, signum, specifies the signal. The second argument, act, points to the new signal action to be installed, while the third argument, oldact, is an optional pointer where the previous signal action will be stored (provided it is not NULL). Note that the rt_sigaction syscall, which glibc transparently calls behind the scenes, takes an additional fourth argument sigsetsize (not shown above), which specifies the size in bytes of the signal sets in act.sa_mask and oldact.sa_mask.

The second and third arguments are both pointers to struct sigaction, which contains an sa_handler field holding the address of the programmer-defined signal handler function. The definition of struct sigaction is shown below:

In the strace excerpt above, the sa_handler field in the struct sigaction pointed to by the act argument, contains the value 0x3f27640. This corresponds to the address of Oracle’s sspterm function and can be verified by examining the Oracle binary with nm, as shown in Listing 5. This means that when the Oracle process receives a SIGTERM, it will call the handler function sspterm.

So now we know how to identify and translate signal handler addresses using strace. A drawback of this approach is that we must trace the creation of a new Oracle process, since the signal handlers are registered when an Oracle process starts. Moreover, manually resolving signal handler addresses to symbols is tedious, so it’s worth exploring ways to script this and examine the signal handler functions in a running Oracle process.

Unfortunately, there is no sigaction array or equivalent structure in user space that exposes a process’s signal handler addresses. They are stored and managed within the kernel and kernel structures cannot be accessed directly from user space (in kernel space, they would be accessible via the task_struct structure).

The problem is that we have no control over running Oracle processes from the outside… unless we bring gdb into play. With gdb, we can attach to a running process and invoke any function or system call, such as sigaction. However, this comes with some prerequisites. We need debug symbols to examine the struct sigaction structure fields more easily and we need to temporarily allocate memory for holding struct sigaction data.

Note that the type definition of struct sigaction printed by gdb looks different from the one in the man page and in Listing 4. An explanation for this is found in the man page, which states: “On some architectures a union is involved […]” (see also [1]). This low-level detail is usually abstracted by the glibc syscall wrapper, so we don’t need to worry about it. However, when accessing memory structures with gdb, we must take it into account.

📝 Note

The sigaction structure supports two types of signal handler functions:

Simple handler: void (*sa_handler)(int);
Extended handler: void (*sa_sigaction)(int, siginfo_t *, void *);

When the SA_SIGINFO flag is not specified in sa_flags, the kernel calls the simple handler; when SA_SIGINFO is specified, it calls the extended handler, which provides additional information in the siginfo_t structure, such as the source and cause of a signal.

A union allows multiple members to occupy the same memory location, which is useful in struct sigaction because only one of the two function pointers, sa_handler or sa_sigaction, is used at a time. By using a union, memory is saved and it is made explicit that the two fields are mutually exclusive. Without a union, space would have to be allocated for both pointers, resulting in unnecessary memory usage.

With these subtleties clarified, we can now examine signal handlers in a running Oracle process.
