Child Cursor Scan Mechanics - An Investigation

2026/06/08

Oracle is a large and complex piece of software, and it often behaves in unexpected ways. During an investigation into a cursor sharing and high version count issue, I encountered several such surprises.

During the investigation, I started wondering about the order in which Oracle scans the list of child cursors: forward, from “older” to “newer”, or backward, from “newer” to “older”. I also wondered about the computational overhead involved in inspecting all child cursors under a parent cursor, assuming a maximum of 8192 child cursors, as permitted by the default value of _cursor_obsolete_threshold.

As is often the case with questions like this, the available information is surprisingly sparse, vague, and at times even contradictory. Therefore, I decided to conduct a systematic experiment and document my findings in this note (all findings and results are based on version 23.26.0). If you don’t have the time or mood to read through all the gory details of this investigation, you can jump directly to the summary.

The experiment is structured as follows:

  1. Create a parent cursor with 8192 child cursors (child #0 through #8191)
  2. Access the last child cursor in the parent’s child cursor list (child #8191) and trace the child cursor access with Oracle’s CURSORTRACE event
  3. Access the last child cursor in the parent’s child cursor list (child #8191) and trace the child cursor access with bpftrace

Careful readers may rightly note that this wording already rests on assumptions, as the exact internal structure used by a parent cursor to maintain its child cursors is not known. It is not publicly documented whether this is a list or, as some sources suggest, an array or a hash table. Anyway, by the end of this post, we’ll have clarity on the exact structure used by Oracle.

When the session cursor cache is enabled, Oracle maintains session-level pointers to child cursors, which allows a session to directly access cursors in the library cache without scanning through the parent’s list of child cursors (see also 2). This optimization kicks in when a statement has been parsed three times and interferes with the experiment; disabling it ensures deterministic and reproducible behavior.

This sets the stage for the next step: capturing a runtime trace to observe how child cursors are scanned and checked, and in what order. The Oracle library cache code is quite well instrumented, and the instrumentation can be enabled using the CURSORTRACE event. The event supports multiple trace levels, although not all of them are publicly documented. However, My Oracle Support note KB829509 provides a good starting point (see also 3). For a detailed discussion of the CURSORTRACE event, see this post (see also 9.

In my tests, I used trace level 0x898244 with the address set to 2763161912. As explained in more detail below, this trace level enables system-wide tracing for the sql statement identified by hash value 2763161912.

The CURSORTRACE event level is a bitmask in which each bit enables a specific tracing feature. Multiple features can be activated by combining their corresponding bit values using a bitwise OR. Trace level 0x898244 means the following bits are set:

  • 0x4: Enable debug level 3 (this includes levels 1 + 2)
  • 0x40: Add cursor to list be traced (this enables tracing only for the sql statement identified by the hash value specified by address)
  • 0x200: Trace cursor sharing criteria
  • 0x8000: Trace sharing criteria failure
  • 0x10000: Trace sharing criteria success
  • 0x80000: Log timestamps (this level is undocumented)
  • 0x800000: Trace child cursor pruning (this trace level is undocumented)

That said, care should be taken with the CURSORTRACE event, as past bugs have been reported in which the trace could not be switched off properly (see 4, for instance).

Before examining the CURSORTRACE output in detail, I expected Oracle to scan the child cursor list in simple forward or reverse sequence, either from child #0 to child #8191 or from child #8191 back to child #0. This expectation was based on a CURSORDUMP trace, which showed that the parent cursor maintains a linked list running from child #0 to child #8191.

This can be observed in a symbolic dump of the kkscs structures. Each structure represents a child cursor in the parent’s child cursor list and links to the next child cursor via a nxt pointer (highlighted in red in the listing below, which shows kkscs entries for child cursors 0, 1, 8190, and 8191). The nxt pointer of the last entry in the list is (nil), indicating the end of the list.

Note that I’m not aware of any alternative way to dump the kkscs structures other than using the CURSORDUMP event (at level 32), which should not be used on a busy system.

Interestingly, the runtime CURSORTRACE output shows a completely different and unexpected behavior: Oracle first scans child #99 down to child #0 in reverse order, and then continues from child #100 up to child #8191 in forward order (the trace excerpt below is annotated and formatted for readability):

This was puzzling enough that I repeated the test case multiple times with varying numbers of child cursors and instance restarts between runs. I also executed it on other instances and in an Oracle 19c environment (19.26), consistently observing the same behavior: when there were 100 or more child cursors, Oracle always scanned the child cursor list in reverse order from child #99 down to child #0, and then in forward order from child #100 up to the highest-numbered child in the list; when there were fewer than 100 child cursors, Oracle only scanned the list in reverse order from the highest-numbered child down to child #0.

At this point, I realized I had not accidentally broken the test case, and that the observed behavior must follow a systematic pattern. There had to be an underlying logic that changes once a 100-child-cursor threshold is reached. But what exactly is Oracle doing, and why doesn’t it scan the child cursor list in linear order from head to tail or tail to head?

To better understand this behavior, I examined the kkscs structures in more detail and discovered a second list linking them via “next” and “prev” pointers, forming a doubly linked list. Internally, this list is referred to as cshsl (child cursor hash list?), and there are 16 such lists per parent cursor, each associated with a hash bucket in a hash table pointed to by the ht pointer.

The child cursor scan code path in kkscsSearchChildList (not shown here) computes a hash value from the pdb name (function kpdbNameHash) and uses it to derive a bucket index in the ht hash table via a modulo-16 operation. This means child cursors created in different pdbs are distributed across 16 child cursor “sublists” according to the pdb name hash.

There are no traces or dumps that provide any details on the cshsl list, so it can only be reconstructed by analyzing the raw memory layout in gdb, which requires quite some manual pointer chasing.

This indicates that cshsl list nodes do not reference kkscs structures directly, but instead point to substructures within kkscs. The kkscs fields of interest are:

  • Offset 0x22 (address 0x58f3c6168): the child number, which is 0x63 (99); this shows that the head of the cshsl list points into the kkscs structure of child #99.
  • Offset 0x50 (address 0x58f3c6198): the “next” pointer to the next node, located at address 0x58f3c59d8 in the cshsl list; as explained earlier, this points to offset +0x50 within the next kkscs structure.
  • Offset 0x58(address 0x58f3c61a0): the “prev” pointer to the previous node in the cshsl list; since we are at the first node in the list, the prev pointer points back to the hash table bucket at address 0x58f55d2e8.

The discovery of the cshsl linked list made me realize the following: if the scan of this list is entirely linear, then it must be the insertion order that determines the order in which child cursors are encountered during a scan.

I therefore wrote a bpftrace script (kkscsSearchChildList.bt: see also 5) to trace the Oracle kernel functions that access the parent’s child cursor list, allowing closer observation of how the list is inserted into and modified at runtime.

In verbose mode, the script emits detailed information about the state of the parent’s child cursor list that is not exposed elsewhere. It also shows that Oracle modifies the list in the kernel function kkshhcins when a new child cursor is added.

The kkshhcins trace shows the state of the previous cshsl node (prev:) and the new node being inserted (curr:). For each node, the first cshsl=["prev","next"] field corresponds to the state on function entry, while the second corresponds to the state on function return. Comparing the two reveals how kkshhcins updates the prev and next pointers when inserting a new node into the list.

When child #99 is inserted, the entry and return states are identical for the prev: node, which represents child #0 at the end of the list. This indicates that kkshhcins does not modify the previous node and performs no pointer updates on it.

In contrast, the insert modifies the curr: node and changes its cshsl pointers:

  • the prev pointer is set to 0x46e107468 (the hash bucket)
  • the next pointer is set to 0x58f9cf0f0 (child #98).

This means the insert links the new node back to the hash bucket via 0x46e107468 and forward to child #98 via 0x58f9cf0f0. This shows that child #99 is inserted at the head of the list, and the following diagram conceptually illustrates how the list is modified.

This now explains the following: Oracle scans the child cursors on the cshsl list in forward order, but the insertion order changes based on the number of existing child cursors on the list:

  • Up to 100 child cursors (child #0 through #99): Oracle inserts the new child cursor at the head of the list.
  • More than 100 child cursors (child #100 through #8191): Oracle inserts the new child cursor at the tail of the list.

The remaining question is why the “insertion threshold” is set to 100 and how it is defined. This is explained by the value of the kdzxdccnum_ SGA variable, which is also exposed by the bpftrace script.

This variable reflects the value of the underscore parameter _xds_max_child_cursors. It defaults to 100 and defines the threshold at which the insertion order changes. If the child cursor being inserted has a child number lower than _xds_max_child_cursors, it is inserted at the head of the list; otherwise, it is inserted at the tail.

This can be verified by changing the parameter to different value and repeating the test case. In the example below, the threshold is set to 5, and then a parent cursor with 10 child cursors is created (note that the parameter can be changed dynamically without restarting the instance).

According to the parameter description, _xds_max_child_cursors specifies the “maximum number of XDS user-specific child cursors”. XDS is an internal abbreviation for Oracle Real Application Security’s Data Security (DS) component (see also 6).

I am not familiar with the Real Application Security feature and therefore cannot explain the rationale behind Oracle’s use of this threshold for determining child cursor insertion order in the parent’s child cursor list. However, note that this behavior is not specific to Oracle 26ai and is identical in 19c (tested on version 19.26, but not shown here).

To connect back to an earlier point, it is worth revisiting the question of what the runtime cost of scanning a child cursor list of up to 8192 entries would actually be. My initial assumption was that Oracle would inspect every child cursor on the list and evaluate the full set of cursor sharing criteria for each child cursor encountered.

This approach would imply a cost of O(n × m), where n is the number of child cursors to check and m the number of cursor sharing criteria checks. Depending on the number of child cursors on the list, this can become a lengthy and costly process, and in the worst case, Oracle would need to inspect and check every child cursor on the list just to determine that it still needs to create a new child cursor anyway.

However, this is not what happens in practice, as Oracle has another neat optimization called Cursor Pruning and you may have noticed clues of this optimization in some of the outputs above.

Internally, this mechanism works by attaching a diagnostic node to a child cursor when a sharing check fails. This node records the reason why a cursor could not be shared and preserves enough information to quickly re-evaluate that same condition later. On subsequent parse attempts, Oracle can use this stored metadata to eliminate unsuitable child cursors early, thereby pruning the search space and reducing repeated full evaluation of all sharing criteria across all cursors.

The exact mechanics are a topic for another time, but the CURSORTRACE output from Listing 7 provides a rough illustration of the underlying behavior. The excerpt below shows a section of the trace file omitted from the earlier listing. It shows Oracle iterating over 8192 child cursors (child #0 through child #8191), where all cursors except the last one are pruned (as indicated by the message Child was pruned). As a result, only this final child cursor undergoes detailed cursor-sharing criteria checks:

Note that most, but not all, of the sharing criteria are exposed in V$SQL_SHARED_CURSOR, and its REASON column contains the diagnostic node data encoded as XML. Moreover, Oracle 26ai introduces a new view, SQL_SHARED_CURSOR_DIAG, that exposes the same information in JSON format (see also 7).

Summary

This post covers a lot of ground, so here are the key takeaways from the investigation:

A parent cursor maintains 16 child cursor “sublists”, internally referred to as cshsl (probably short for cursor hash list). These lists are organized through a hash table, with the target bucket determined by pdb_name_hash % 16, where pdb_name_hash is a hash value derived from the pdb name. Note that the bucket count of 16 is a fixed constant in the oracle binary and cannot be changed or reconfigured at runtime. If multiple pdb names map to the same bucket, the corresponding list contains child cursors from more than one pdb. However, during a child cursor list scan, entries whose pdb does not match the target pdb are skipped and not checked further.

The following diagram provides a conceptual illustration of how a parent cursor maps child cursors from different pdbs into separate child cursor lists (cshsl). It also shows how a singly linked list traverses the child cursors in ascending child-number order.

As long as the total number of child cursors is less than or equal to the threshold defined by _xds_max_child_cursors (which defaults to 100), newly created child cursors are inserted at the head of the lists. Once the total number of child cursors exceeds _xds_max_child_cursors, new child cursors are instead inserted at the tail of the lists. In an extreme scenario, a single pdb could create 100 child cursors that all end up in the same list, where they are inserted at the head. Any child cursors subsequently created by other pdbs would then be inserted at the tail of their respective lists.

Cursor sharing criteria checks do not incur O(n × m) complexity because of the Cursor Pruning optimization, which allows Oracle to eliminate unsuitable child cursors early without evaluating all cursor sharing criteria for each child. Without this optimization, child cursor scan costs would increase significantly as the number of child cursors increases.
