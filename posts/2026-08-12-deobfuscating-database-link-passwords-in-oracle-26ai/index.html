Deobfuscating Database Link Passwords in Oracle 26ai

2026/08/12

I recently encountered a scenario where I needed to deobfuscate the password of a database link user in Oracle 26ai. So, my plan was to quickly execute the db_link_password_decrypt_standalone.sql script written by Hatem Mahmoud (see also 1), but unfortunately, it failed with an error on Oracle 26ai.

The following test case shows the problem:

According to this blog post, in which Hatem describes in detail how Oracle obfuscates database link passwords (see also 3), the obfuscated password is stored in the passwordx column of the sys.link$ table. However, this appears to have changed in Oracle 26ai, where the passwordx column no longer contains a value:

A quick look at sys.link$ and its columns reveals that Oracle Database 26ai introduces two new columns, spare1 and spare2:

Interestingly, the value exposed in the new spare1 column closely resembles the value previously exposed in passwordx on 19c:

Note that the new spare1 column is defined as a BLOB, whereas passwordx is defined as a RAW. A note on this page by René Nyffenegger (see also 6) points out that this change to the sys.link$ table is documented in Oracle’s dbmsmetu.sql script, and indeed, the script contains the following remark (lines 1238–1240 in an Oracle 23.26.2 home):

Sure enough, replacing passwordx with spare1 in Hatem’s script is enough to make database link password deobfuscation work in Oracle 26ai:

I’ve uploaded a modified version of the original script to my GitHub repository (see also 7). The modified version works on both Oracle 19c and Oracle 26ai, and I’ve also submitted a pull request to have the change incorporated into the original script.

Note that you can still use the pl/sql procedure db_link_password_decrypt installed by the script db_link_password_decrypt.sql (see also 2) on Oracle 26ai. You just need to pass the value of spare1 value instead of passwordx in the password_link argument, for example:

On a related note, if you’d like to understand how Oracle obfuscates scheduler credential passwords and how they can be deobfuscated, this post provides a detailed explanation of the process (see also 8).

Finally, note that Oracle recommends encrypting sensitive credential data stored in the data dictionary, such as database link passwords or scheduler credentials. For further details on enabling dictionary credential encryption, refer to 9.
