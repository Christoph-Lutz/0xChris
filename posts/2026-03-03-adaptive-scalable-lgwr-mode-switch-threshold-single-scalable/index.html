Adaptive Scalable LGWR Mode Switch Threshold Single->Scalable

2026/03/03

Oracle fundamentally reworked and redesigned the LGWR architecture in 12c. In earlier versions, LGWR ran as a single process, whereas Oracle 12c and later can dynamically switch between a single LGWR process and multiple LG worker processes operating concurrently and in parallel. That is, the LG worker processes can handle different redo write requests in an overlapping fashion, work on a single redo write request in parallel, or do both at the same time — though the LGWR write mechanics are a topic for another post.

This architectural enhancement primarily aims to increase redo write throughput and goes by the rather tongue-twisting name Adaptive Scalable LGWR, sometimes also referred to as “Multiple LGWR”. When multiple LGWR processes are active, the LGWR process acts as a log write coordinator and delegates all I/O work to multiple LGnn worker processes. For further information on this aspect of LGWR, refer to this investigation carried out by Frits Hoogland (see 1), which covers LGWR and LG interaction in great detail.

This post focuses on the heuristics and conditions that determine when exactly LGWR decides to switch from “single mode” to “scalable mode” (using multiple concurrent/parallel worker processes), which are not officially documented by Oracle.

Information about LGWR mode switches can be found in the LGWR trace file, showing entries like the following when multiple LGWR processes are enabled or disabled:

The excerpt above shows the exact timestamps of when LGWR mode switches occurred, along with a set of undocumented statistical numbers that play a role in the decision-making to enable and disable LG worker processes. The goal of this post is to explain what this all means in detail.

Besides the LGWR trace file, the following sysstat counters also provide clues about whether multiple LGWR processes are active or not:

  • redo writes adaptive worker: total number of redo writes in adaptive scalable mode
  • redo writes adaptive all: total number of redo writes in single and adaptive scalable mode

The difference between redo writes adaptive all and redo writes adaptive worker represents the number of redo writes issued in single mode.

Now that the stage is set, let’s examine the LGWR decision-making heuristics in more detail.

Mode Switch Threshold Single->Scalable

Before going into the gory details, two points should be noted. First, what follows describes internal behavior that is not officially documented by Oracle and is therefore subject to future change. All investigations were performed on Oracle 19.26 in a RAC environment on Exadata X8M and X9M systems with Exadata software version 25.1.7.

Second, a great difficulty in explaining internal Oracle behavior is that it can feel like falling down a rabbit hole, branching off in all directions — but we’ve got to start somewhere. So, let’s assume a system running in steady state, meaning there have already been a number of mode transitions from single to scalable mode and back.

In that case, covering the basic scenario, the LGWR switch heuristics transition from single to scalable mode when the current average redo rate exceeds twice the average redo rate recorded at the time of the last switch from scalable mode back to single mode.

This was a bit of a long-winded explanation. Let’s put the decision criteria into a formula and systematically work through its components, branching off where necessary:

The redorate is a smoothed moving average of the redo size system statistic and is computed by the CKPT process every three seconds (in function kcrfw_slave_adaptive_cronjob, which calls kcrfw_slave_adaptive_saveredorate to compute the average).

Breaking down the formula:

  • delta: difference in redo size between the current and previous measurement, representing the redo generated since the last check
  • curr: current value of the redo size sysstat counter
  • prev: previous value of the redo size sysstat counter (from the last measurement)
  • deviation: difference between the latest measurement and the current moving average, can be positive or negative (upward or downward adjustment)
  • redorate: smoothed moving average of the redo rate
  • 2/129: correction factor

The formula incrementally updates the redorate moving average using the deviation between the latest measurement and the current average, and applies a small correction factor of 2/129 (~0.0155) on each update. Note that the redorate update can be positive or negative, allowing the moving average to adjust both upward and downward. The smoothing factor controls how quickly the moving average adapts to changes in redo generation rate and ensures gradual convergence toward current conditions while dampening short-term volatility.

The switch value represents the redorate that was measured and recorded at the time of the last transition from scalable mode back to single mode.

Note that all internal counters, such as redorate and switch, are stored in the SGA structure kcrf_slave_info_, which is not exposed through any V$ view or X$ table.

_adaptive_scalable_log_writer_enable_worker_threshold is an underscore parameter with a default value of 200. According to its description the parameter value is expressed as a percentage (see x$ksppi.ksppdesc), which explains the division by 100 in Formula 1 above.

So, to summarize, LGWR switches from single to scalable mode when the current redo rate moving average exceeds twice the value measured at the last transition from scalable back to single mode. Let’s examine the numbers from the trace excerpt shown in Listing 1 to verify this:

  • redorate=1912371
  • switch=423934

The redo rate of 1912371 is greater than the threshold of switch * 200/100 = 423934 * 2 = 847868 and therefore, LGWR decides to transition from single to scalable mode as indicated by the single->scalable trace file entry. Also note that the decision-making logic is evaluated in the Oracle kernel function kcrfw_slave_adaptive_updatemode.

This concludes the basic scenario. Exadata X8M and X9M systems using the PMEM log feature exhibit a special-case behavior, which will be explained later.

Mode Switch Safety Checks

Oracle has built-in guardrails to prevent LGWR from constantly switching and oscillating between different modes, as this could introduce unpredictable behavior. Therefore, a mode switch is only evaluated if the following preconditions are met.

The parameter _adaptive_scalable_log_writer_sampling_time defines the minimum interval, in seconds, between evaluations for a mode switch. It defaults to 3, meaning LGWR evaluates whether to switch modes at most once every 3 seconds.

The parameter _adaptive_scalable_log_writer_sampling_count defines the minimum number of log writes between evaluations for a mode switch. Its default value is 128, meaning LGWR evaluates a mode switch at most once every 128 log writes.

arbiter is a counter initialized to 3 and is decremented each time the mode switch condition is met; that is, when the redo rate exceeds the switch threshold, as defined in Formula 1. The value 3 is hard-coded in function kcrfw_slave_adaptive_updatemode and cannot be changed or configured.

Considering these checks, mode switches cannot occur more frequently than roughly every 9 seconds (3 seconds × 3 arbiter decrements), provided that redo log write activity is sufficient to meet the sampling count condition of 128 redo writes per evaluation.

Technically, these preconditions are implemented as guard clauses in function kcrfw_slave_adaptive_updatemode, which, if not met, result in an early return from the function.

Mode Switch Threshold Aging

While we now understand the heuristic that decides about a switch from single to scalable mode, the story isn’t complete yet, as there is another dynamic at play.

The switch threshold is not static, LGWR gradually ages and decreases it over time when running in single mode, making a transition from single to scalable mode increasingly likely as time passes.

The reason for this isn’t obvious, because we haven’t yet covered the reverse heuristic that switches from scalable mode back to single mode (I’ll write about that in another post). For now, just note that switching back from scalable to single mode considers the average redo write time rather than the average redo rate and in short, LGWR switches back to single mode when it determines that redo writes are faster in single mode than in scalable mode.

So, LGWR still records the average redo rate in switch when transitioning from scalable mode back to single mode, but the switch-back decision is not influenced by the redo rate at all. As a result, there can be cases where the redo rate in scalable mode is relatively high, yet LGWR still switches back to single mode because the decision is driven solely by the redo write time. If the redo rate happens to be exceptionally high at that moment, future transitions from single to scalable mode may become unlikely or, in extreme cases, could be prevented entirely. This situation can be mitigated by gradually aging the switch threshold over time.

The switch threshold aging is controlled by the parameter _adaptive_scalable_log_writer_enable_worker_aging, which has a default value of 999,900. The parameter description explains that the value is expressed in “per millionth” units (see also x$ksppi.ksppdesc).

Exadata X8M and X9M Special Case — PMEM LOG and Fast Log File Sync

Exadata X8M and X9M systems feature a special commit optimization, the Fast Log File Sync (sometimes also referred to as the “Fast Sync”). The Fast Log File Sync was developed for use with PMEM devices, which provide I/O latencies in the range of a few microseconds. These devices are so fast that committing FG processes do not wait for LGWR to notify them of redo write completion. Instead, they put themselves to sleep for a very short duration (slightly longer than the expected LGWR redo write time) and then actively and fairly aggressively poll LGWR’s redo write progress. For further background information, see [2].

Intel discontinued the production of PMEM and therefore, newer Exadata X10M and X11M systems are no longer equipped with PMEM devices. However, some of the older X8M and X9M systems are still around, which is why it’s useful to understand their behavior in detail.

On Exadata X8M and X9M, Oracle checks at instance startup whether the Fast Log File Sync optimization and the Exadata PMEM log are enabled and, if so, sets max_log_write_parallelism to a fixed value of 1. The parameter _max_log_write_parallelism defines the number of LGnn worker processes that can work on a redo write request in parallel. Its default value is derived from the maximum number of public redo strands using ceil(_log_parallelism / 4).

The check and the change to max_log_write_parallelism are both carried out in the function kcrfw_dax_is_smart_log, as can be observed with the bpftrace script kcrfw_dax_is_smart_log-max-lwp.bt(start the script before restarting the instance):

In this example, max_log_write_parallelism was set to 4 on entry to the function kcrfw_dax_is_smart_log (due to the default of parameter _max_log_write_parallelism = 4 on my test system), but when the function returned, the value had changed to 1.

Why is this all relevant in the context of Adaptive Scalable LGWR? The reason is that LGWR’s decision-making heuristic includes a special check: it looks at the runtime value of _max_log_write_parallelism (stored in the SGA structure kcrf_slave_info_) and, if it is 1, applies a special adjustment factor to the switch threshold calculation.

With max_log_write_parallelism set to 1, it applies an adjustment factor of 2 and this effectively doubles the threshold in the decision making logic:

  • max_log_write_parallelism == 1 ? → redorate > switch * 200/100 * 2 → redorate > switch * 4
  • max_log_write_parallelism > 1 ? → redorate > switch * 200/100 * 1 → redorate > switch * 2

This means, with the Exadata PMEM log enabled and max_log_write_parallelism set to 1, the average redo rate must be 4 times greater than the switch threshold before LGWR transitions from single to scalable mode.
