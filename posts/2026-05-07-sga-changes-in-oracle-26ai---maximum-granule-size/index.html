SGA Changes in Oracle 26ai - Maximum Granule Size

2026/05/07

All memory components in the Oracle SGA are internally managed in fixed-size units called granules. They were introduced back in Oracle 9i as a standardized allocation unit that enables an Oracle instance to dynamically grow and shrink memory pools such as the buffer cache and shared pool at runtime in response to workload demands.

Memory for each pool is always allocated in whole granule units, and each pool requires at least one granule. Some memory pools can be subdivided into subpools and durations, and each of these smaller units requires a minimum of one granule. This means that a high number of subpools, and durations results in a higher memory footprint on a system. For a more detailed introduction and description of SGA granules, refer to sources 1, 2, and 3.

Historically, the granule size has varied with the Oracle version and total SGA size. It can also vary across platforms, but this post focuses on Oracle 26ai running on Linux, and compares its behavior to Oracle 19c where appropriate.

My Oracle Support note KB119333 (source 5) further explains that versions prior to 18.9 included the size of the in-memory column store (IMC) defined by parameter inmemory_size in the SGA size whereas 19c and later no longer include it. This means that as of 19c, the inmemory_size value must be subtracted from the sga_target or memory_target value to determine the granule size.

Based on this information, we would expect a granule size of 128M for an instance with an SGA size of 48G (and no IMC configured). A check on 19c (19.26) shows that the information from KB119333 still applies:

However, running the same check on Oracle 26ai (23.26.0.0) yields a different result, showing that Oracle now uses a granule size of 64M rather than 128M:

Apparently, something has changed in Oracle 26ai, and the change has not been reflected in the Oracle docs. So, time for an investigation and a closer look.

Interestingly, KB119333 also mentions a “granule size lookup table” without providing further details on what it is or where it is stored.

A low-level examination of the Oracle binary reveals a symbol named ksmg_gran_sz, which is worth taking a closer look at using the readelf utility (the symbol’s mnemonic can be interpreted as Kernel Service Memory Granule Granule Size).

The output above from version 23.26.0.0 shows that the symbol starts at virtual memory address 0x198515c0 and has a size of 64 bytes. Assuming a word size of 8 bytes, it spans 8 words, i.e., it can store 8 elements of 8 bytes each.

This looks very much like the “granule size lookup” table mentioned in KB119333, since the granule sizes perfectly match those listed in that note (see also Table 1 above).

This raises two questions: how does Oracle use the “granule size lookup table”, and why does Oracle 26ai use a granule size of 64M whereas Oracle 19c used 128M?

To understand this, we need to examine a second symbol, ksmg_sga_sz, using the same techniques as above, starting again with readelf:

Similar to ksmg_gran_sz, ksmg_sga_sz is also 64 bytes in size and so can hold eight 8-byte values as well. The second gdb command below also interprets ksmg_sga_sz as an array of eight 8-byte elements:

Note that I added additional comments to the output showing the values in gigabyte units, and, interestingly, they exactly match the SGA size thresholds listed in KB119333 (see also Table 1 above). Moreover, each SGA size threshold in the ksmg_sga_sz array maps to the granule size at the corresponding index in the ksmg_gran_sz array.

So what Oracle did through version 19c is something like: scan the ksmg_sga_sz array until the SGA size threshold at the current index position becomes smaller than the SGA size; once the first smaller threshold (or the array terminator) is reached, return the granule size from ksmg_gran_sz at the same index.

According to the lookup logic and the values in the ksmg_sga_sz and ksmg_gran_sz arrays, Oracle 26ai should use a granule size of 128M for an SGA size of 48G. However, as shown in Listing 2, the observed granule size in Oracle 26ai is 64M.

The reason for this is that Oracle 26ai introduces a new hidden parameter, _max_def_granule_size, which defaults to 64M (67108864 bytes) and defines an upper bound on the granule size. This limit is enforced by the internal callback function ksmg_max_def_gran_size_chk, which applies the following constraints:

  • if _max_def_granule_size is set to a value below 4M, it is rounded up to 4M
  • if it is set to a value above 512M, it is rounded down to 512M
  • if it is set within the range of 4M to 512M and is not a power-of-two value, it is rounded up to the next power-of-two value (for instance _max_def_granule_size=6M is rounded up to 8M)
  • if it is lower than db_files * 144 + 536, it is rounded up to the next power-of-two value above that value. Note that this is a reasonable approximation, as the exact formula is quite complex and not worth analyzing further at this point, since it is only relevant when the number of db files is very large (meaning ten thousands of datafiles) and _max_def_granule_size is set to a relatively low value such as 4M or 8M

If you set _max_def_granule_size=512M, the granule size lookup logic behaves the same as in Oracle 19c.

Let’s look at some examples by tracing callback function ksmg_max_def_gran_size_chk using script ksmg_max_def_gran_size_chk.bt (see source 7) during instance startup.

Example 1:

  • sga_target=48G
  • _max_def_granule_size not set (default setting of 64M)
  • db_files=200 (default setting)

The trace output shows the following:

  • lines 7 - 9: kspges checks if _ksmg_granule_size is set; it is not at this stage, so it returns 0.
  • lines 10 - 12: kspges checks if _max_def_granule_size is set; it is not at this stage, so it returns 0.
  • line 13: Oracle uses the _max_def_granule_size default value of 64M (67108864 bytes)

Example 2:

  • sga_target=48G
  • _max_def_granule_size=512M (same maximum granule size as in Oracle 19c)
  • db_files=200 (default setting)

In this example, _max_def_granule_size was set to 512M (536870912 bytes). The call to kspges (lines 10 - 12) indicates that a parameter value has been specified by returning 1, and Oracle therefore uses the specified value 536870912 (512M) as the maximum limit (line 13).

Example 3:

  • sga_target=48G
  • _max_def_granule_size=4M
  • db_files=40000

Note that in this example, the script was called with the verbose option to also show the calls to kcfmingran and kcbwmingran. These are helper functions that can override the maximum default granule size if Oracle considers it too low.

The helper function called first, kcfmingran, factors in a minimum size for every datafile based on the db_files setting. In this case, db_files is set to 40000 and therefore returns a value of 5760624 (lines 8 and 10). This is slightly off from the result given by the earlier mentioned approximation formula (db_files * 144 + 536 = 5760536), but still sufficiently close for our purposes. More importantly, the value 5760624 returned by kcfmingran exceeds the specified _max_def_granule_size of 4M and is not a power-of-two value, Oracle therefore rounds it up to 8388608 (8M), as shown on line 16.

The second helper function, kcbwmingran, always returns the hard-coded value of 3072 in Oracle 26ai, so it has no practical relevance. Oracle uses the maximum value returned by either kcfmingran or kcbwmingran, and with a default db_files setting of 200, the value returned by kcfmingran is higher than 3072 (200 * 144 + 536 = 29336).

Note that the parameter _max_def_granule_size only defines the maximum limit for the granule size. The effective granule size is determined via parameter _ksmg_granule_size, which already existed in Oracle 19c (and earlier versions). Its value is initialized at instance startup through the callback function ksmglgchk, which performs an SGA size-to-granule-size mapping using a lookup logic based on the ksmg_sga_sz and ksmg_gran_sz arrays, as described above.

In Oracle 26ai, however, ksmglgchk additionally calls a new function, ksmg_adjust_gransize, which enforces the cap on the computed granule size, defaulting to 64M unless overridden by a user-defined limit specified in _max_def_granule_size.

If _ksmg_granule_size is set to a user-specified value, the _max_def_granule_size check is bypassed (that is, the function ksmg_adjust_gransize is not called during instance startup). In other words, setting _ksmg_granule_size disables the maximum granule size cap.

For parameter _ksmg_granule_size, the following constraints apply:

  • the minimum value is 1M, a value lower than that is rounded up to 1M (note that 1M is a pure technical limit, on my test system a granule size of 1M resulted in an ORA-64 error at instance startup: “object is too large to allocate on this O/S (1,1539816,sys event stats)”).
  • if set to a value above 512M, it is rounded down to 512M
  • if it is set within the range of 1M to 512M and is not a power-of-two value, it is rounded up to the next power-of-two value (for instance _ksmg_granule_size=6M is rounded up to 8M)

Let’s look at some traces again, this time using the bpftrace script ksmglgchk.bt (see source 8) to trace calls to ksmglgchk.

Example 4:

  • sga_target=48G (according to the granule size lookup table, this should result in a granule size of 128M)
  • _max_def_granule_size not set (default setting of 64M)

The trace output (formatted for readability) shows the following:

  • lines 7 - 9: kspges checks if _ksmg_granule_size is set; it is not at this stage, so it returns 0.
  • lines 10 - 11: Oracle calls ksmg_estimate_nonimc_sga_size to estimate the SGA size (excluding the IMC), which is 48G (51539607552 bytes) in this case
  • line 12: Oracle calls ksmg_adjust_gransize; the first parameter is the granule size from the lookup table (128M or 134217728 bytes).
  • lines 13 - 18: ksmg_adjust_gransize checks if _enabled_pdb_isolation and _max_def_granule_size are set using kspgip and kspges; neither of these parameters is set, so both functions return 0
  • line 19: ksmg_adjust_gransize returns the default maximum granule size of 64M (67108864 bytes)
  • line 20: ksmglgchk uses the default maximum granule size of 64M (67108864 bytes) returned by ksmg_adjust_gransize

This example proves that Oracle 26ai still uses the same granule size lookup logic as in 19c and determines a granule size of 128M, which then gets adjusted because it exceeds the maximum limit imposed by _max_def_granule_size.

Example 5:

  • sga_target=48G (according to the granule size lookup table, this should result in a granule size of 128M)
  • _max_def_granule_size=512M (same maximum granule size as in Oracle 19c)

With _max_def_granule_size set to 512M, Oracle uses a granule size of 128M (134217728 bytes), as shown on lines 22 and 23. This matches the granule size from the lookup table and reflects the same behavior as in Oracle 19c.

Note that Oracle calls kspges on line 16 to check whether _max_def_granule_size has been set; the return value of 1 on line 18 indicates that it has. It then calls kspgzp to retrieve the maximum granule size limit from the spfile, which is 512M (536870912 bytes) and therefore higher than the value of 128M (134217728 bytes) passed into ksmg_adjust_gransize (line 12). This means, the value retrieved from the granule size lookup table is below the maximum granule size and is therefore used without further adjustment.

Example 6:

  • sga_target=48G (according to the granule size lookup table, this should result in a granule size of 128M)
  • _max_def_granule_size=32M
  • _ksmg_granule_size=209715200 (this corresponds to 200M, but the _ksmg_granule_size parameter doesn’t support human-readable format specifiers)

In this scenario, the limit imposed by _max_def_granule_size is lower than _ksmg_granule_size, and _ksmg_granule_size is not a power-of-two value. However, the trace shows that the maximum granule size limit is not enforced (that is, the function ksmg_adjust_gransize is not called), and Oracle uses the value from _ksmg_granule_size, rounded up to the next power-of-two value, which is 256M (268435456 bytes). This proves that the _ksmg_granule_size setting takes precedence and overrides _max_def_granule_size.

Why did Oracle change the maximum default granule size in 26ai and decide to cap it at 64M by default? Unfortunately, we don’t know, because this is an undocumented internal change, so we can only speculate. I suspect part of the motivation relates to this SGA change in Oracle 26ai (see source 9) where, depending on system configuration, the number of subpools and durations may increase compared to earlier versions. Since each of these smaller units requires at least one granule, a smaller maximum granule size could help reduce memory overhead.

Another reason may be that the old maximum size of 512M turned out to be too large and inflexible for reshuffling memory across different memory pools. So, this change may aim to make reshuffling operations more gradual and less intrusive, as eight smaller 64M reallocations may be less disruptive than one large 512M reallocation.
