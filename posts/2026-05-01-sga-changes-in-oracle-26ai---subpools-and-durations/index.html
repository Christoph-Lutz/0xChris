SGA Changes in Oracle 26ai - Subpools and Durations

2026/05/01

Oracle’s SGA memory pools have undergone regular changes over the years and across different versions. Oracle 26ai is no exception and introduces another redesign of SGA memory pools, such as the shared pool.

This first part of this post explains how Oracle 26ai changes the number of subpools and durations in various SGA memory pools compared to Oracle 19c, while the second part shows how to trace and observe them using low-level probes. For additional background information on this subject, refer to sources 1, 2, and 3.

All investigations described in this post were carried out on Oracle versions 23.26.0.0 and 23.26.1.0.

Subpools and Durations in Oracle 26ai

Oracle 26ai introduces the following changes to subpools and durations:

  • The shared pool can be divided into 31 subpools (in Oracle 19c, the limit was 7 subpools).
  • The large pool, streams pool and NUMA pool can also be divided into subpools (in Oracle 19c, this was only possible for the shared pool).
  • The number of subpools in the shared pool, large pool, streams pool, and NUMA pool can be configured via underscore parameters (in Oracle 19c, this was only possible for the shared pool via _kghdsidx).
  • There are now 3 durations per shared pool subpool (in Oracle 19c there were only 2).
  • The streams pool can also be divided into multiple subpools if _enable_streams_pool_subpools=true (default is false). This functionality was backported to 19.16 in fix 34010877, where it can be enabled by setting _bug34010877_enable_streams_pool_subpools=true (see also source 4).

Table 1 provides an overview of the new underscore parameters and their associated internal callback functions that Oracle invokes at instance startup. These callback functions compute the number of subpools and initialize the corresponding underscore parameters with their default values when automatic memory management is enabled (that is, when either sga_target or memory_target is set). In addition, the primary factors influencing how Oracle determines the number of subpools are cpu_count and the SGA size; the detailed mechanics and formulas are discussed later.

Note that the number of durations per subpool is hard-coded and cannot be configured via underscore parameters. Moreover, each subpool is protected by a separate shared pool latch. Since Oracle 26ai can use a higher total number of subpools, this also explains why it may have more shared pool latches than earlier versions

The underscore parameters and callback functions have rather cryptic names and, as with many internal Oracle constructs, follow a naming logic that is not publicly disclosed, but which I assume, reflects the following mnemonic scheme:

  • kghdsidx: Kernel Generic Heap Descriptor Index(es)
  • ksmc<pool>sdxchk: Kernel Service Memory Create <pool> Subpools Descriptor indeX Check, where pool identifies the target memory pool: sp = shared pool, lp = large pool, str = streams pool, numa = NUMA pool
📝 Java Pool

Unlike the other pools, Oracle 26ai introduces no new underscore parameter for the java pool. While I have not investigated this further, the parameter descriptions (see `x$ksppi.ksppdesc`) suggest that the shared pool latches used for the shared pool and large pool are also shared with the java pool. However, I am not aware of any structural changes in the java pool in Oracle 26ai compared to earlier releases.

If no pool size is specified, Oracle computes a pool-specific minimum size for each pool derived from the SGA size; if a pool size is specified, Oracle uses it, provided that it exceeds the pool-specific minimum size.

A few things worth noting: The SGA size used in the minimum pool size computation does not include the size of the in-memory column store (IMC). Moreover, the pool-specific minimum sizes are internal, hard-coded percentages that are passed as arguments to the parameter callback functions listed in Table 1, meaning they cannot be changed or configured. Finally, unlike the other pools, the size of the NUMA pool is not controlled by a “pool_size” parameter, but is instead derived from the shared_pool_size parameter.

With this system configuration, Oracle 26ai creates 8 shared pool subpools, whereas Oracle 19c capped this at 7, as this was the limit imposed by the undocumented parameter _kghdsidx_count in Oracle 19c.

📝 Parameter _kghdsidx_count

The underscore parameter `_kghdsidx_count` still exists in Oracle 26ai and is backed by the callback function ksmcsdxchk. However, in Oracle 26ai this function appears to be a placeholder that simply returns the value 1.

Interestingly, the _kghdsidx_count parameter can still be used in Oracle 26ai and, when set, it divides the shared pool into the specified number of subpools, with the same upper limit of 7 as in Oracle 19c. However, it does not change the number of durations per shared pool subpool (which remains three), nor does it affect the number of subpools in the other memory pools.

I suspect the _kghdsidx_count parameter remains for backward compatibility, but I have not investigated its purpose and behavior further in Oracle 26ai.

What are the advantages and disadvantages of a higher number of subpools in Oracle 26ai compared to earlier versions? Generally speaking, a higher number of subpools improves concurrency, as contention for shared pool latches can be distributed across multiple subpools. The drawback, however, is that a higher number of subpools results in smaller average subpool sizes, assuming equally sized subpools. Furthermore, non-uniform subpool sizes may lead to memory allocation and free space imbalances across subpools. Both scenarios can increase memory pressure on individual subpools, potentially triggering expensive memory resize operations during which Oracle reallocates granules from the buffer cache to the shared pool as part of automatic SGA resizing. Such operations can temporarily stall a busy system. Additionally, smaller or imbalanced subpools may also lead to ORA-4031 errors.

Tracing How Oracle 26ai Determines the Number of Subpools

In Oracle 26ai, the new underscore parameters that determine the number of subpools in the shared pool, large pool, streams pool, and NUMA pool are backed by the callback functions listed in Table 1, which are invoked when an Oracle instance starts.

The callback functions are essentially just small wrapper functions that delegate the computation to the common helper function ksmcpoolsdxchk (Kernel Service Memory Create Pool Subpool Descriptor Index Check), which has the following signature:

The function arguments have the following meaning (based on my interpretation and understanding; the actual argument names in the Oracle source code may differ):

  • unk: pointer to a memory address, the exact purpose is unclear to me.
  • sga_min_pct: percentage of the SGA size used to derive the default minimum pool size (excluding the IMC size and used only if no pool size is specified in the spfile or if the specified value in the spfile is below the computed default minimum).
  • pool_prm_idx: spfile pool_size parameter used to determine whether a minimum pool size is defined; it is specified as an index into the parameter table, corresponding to x$ksppi.indx - 1 (Oracle 26ai maps pools to pool_size parameters as follows: shared pool → shared_pool_size, large pool → large_pool_size, streams pool → streams_pool_size, and NUMA pool → shared_pool_size).
  • max_subpools: the maximum possible number of subpools.

Based on this, we can use uprobes to instrument the ksmcpoolsdxchk helper function and print its argument values at runtime during instance startup. This allows us to closely observe what Oracle is doing internally when deriving the number of subpools at instance startup. The example output shows the function call flow executed by the callback function ksmcspsdxchk in Oracle 26ai when computing the number of subpools for the shared pool.

  • line 8: the callback function ksmcspsdxchk calls the helper function ksmcpoolsdxchk with arguments 0x7fde6ccc9578, 25, 320, and 31
  • lines 9 - 11: this is essentially a more detailed description of the function arguments.
  • lines 12 - 13: the helper function calls ksmg_estimate_nonimc_sga_size to determine the SGA size; as the name suggests, it returns the SGA size excluding the IMC component and returns 51539607552 bytes (48G) in this case.
  • lines 14 - 16: the helper function calls kspgzp, which checks if the parameter with number 320 (shared_pool_size) is set in the spfile; in this case it is set to 32G, so kspgzp returns the value 34359738368.
  • lines 17 - 18: the helper function calls ksb_cpu_eff_thread_count_compute to return the number of CPUs on this instance, which is 128.
  • lines 19 - 34: the tracing script was called with the verbose option and therefore prints a step-by-step walkthrough of how Oracle computes the number of subpools in the shared pool. In this case, the cpu cap and the memory cap both exceed the maximum possible number of subpools, which is why Oracle caps the value at 31.
  • line 35: the helper function returns the value 31, indicating that 31 shared pool subpools should be created.

Note that the script shows similar outputs and computations for the large pool, streams pool, and NUMA pool (not shown in the excerpt above; the study of these is left as an exercise for the reader).

The section starting with heap name="sga heap" in the excerpt above provides a summary of all 31 shared pool subpools on lines 6 - 36, with one line per subpool. Each line begins with ds for index n (where n is the descriptor index 1 - 31), meaning each descriptor index entry corresponds to a subpool.

In Oracle 26ai, each subpool contains three durations, so each descriptor index entry lists three memory addresses corresponding to the duration descriptors within that subpool. The gap between the second and third address indicates that a duration three is not present (technically, this corresponds to duration number 2, as Oracle uses zero-based numbering for durations, as we’ll see shortly).

Shared pool durations are identified by a number pair (s, d), where s denotes the subpool and d the duration. Note that there is no duration number 2 in Oracle 26ai. Thus, the durations in subpool 1 correspond to (1,0), (1,1), and (1,3); the durations in subpool 2 to (2,0), (2,1), and (2,3), and so on.

Just one last note before closing: the last line in the excerpt above shows that Oracle is using a granule size of 64 MB (as indicated by granule size 67108864). This is another change introduced in Oracle 26ai, as the granule size for this SGA size (48G) would have been 128M in Oracle 19c. I’ll cover this detail in a future post.
