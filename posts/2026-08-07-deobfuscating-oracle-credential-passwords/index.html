Deobfuscating Oracle Credential Passwords

2026/08/07

In Oracle, credentials are database objects that store a username and password pair for authentication when executing external procedures (extproc callouts), remote jobs, and external jobs (see also 1). More recent Oracle releases also support using credentials with database links (see also 2 and 3).

Credentials are created with the dbms_credential.create_credential procedure, and the associated passwords are stored in obfuscated form in the data dictionary (see also 4). However, Oracle does not publicly disclose the details of the internal obfuscation mechanism and I could not find any publicly available information about it either, which motivated me to take a closer look.

Note that the findings in this post apply to the following Oracle releases:

  • Oracle 19c (tested on 19.28 and 19.30)
  • Oracle 26ai (tested on 23.26.0 and 23.26.2)

If you are not interested in the low-level technical details, you can jump directly to the section Password Obfuscation and Deobfuscation Step by Step, which summarizes how Oracle obfuscates and deobfuscates credential passwords.

Note that the function flow trace in Listing 7 is limited to key Oracle kernel and library functions of interest and does not capture the complete call path executed by Oracle when creating a new credential. The prefixes used in the traced function names provide a basic indication of the components involved and the functionality implemented by these functions:

  • jsci: Oracle job scheduler functions
  • zt: Security and encryption/decryption related functions from Oracle’s libnnzsrv.so library
  • aesni: Low-level OpenSSL encryption functions that are optimized to use AES-NI hardware acceleration

The trace also captures the values of function arguments supplied when the functions are invoked. Some of these arguments are pointers, and in some cases, it is necessary to observe how the function modifies the memory areas they reference. For this purpose, the trace prints the referenced data on function entry and function return. For example, buf e: represents the data in the memory area pointed to by buf on function entry, while buf r: represents the data on function return.

Let’s start the function flow analysis by looking at the aesni_set_encrypt_key and aesni_cbc_encrypt functions and their arguments. Both functions are low-level OpenSSL routines that use the processor’s AES-NI instruction set to perform hardware-accelerated AES encryption.

The optimized aesni functions take the same arguments as their non-optimized counterparts, which, according to the man pages (see also 6), are as follows:

The aesni_set_encrypt_key function accepts a userKey pointer and key length defined by bits. In this case, bits is set to 128, meaning the provided encryption key consists of 128 bits (16 bytes) and is expanded into an AES key schedule stored in an AES_KEY structure pointed to by the key argument. The key schedule contains the round keys derived from the original AES key (userKey) and is used by subsequent AES encryption routines to perform the individual AES encryption rounds (see also 7).

Note that the 16-byte sequence pointed to by userKey matches the sequence highlighted in red in the decoded base64 output shown in Listing 6. This means that the 16 bytes starting at offset 1 and ending at offset 16 (using zero-based indexing) in the decoded base64 output contain an AES-128 encryption key. We will examine the origin and generation of the key value (userKey) shortly, but first focus on how the key is used by the aesni_cbc_encrypt function.

The function aesni_cbc_encrypt reads a 16-byte block (length=16) from the memory area pointed to by in and encrypts it using the expanded AES_KEY structure pointed to by key. The CBC initialization vector used for the encryption is provided through the ivec argument. The resulting ciphertext is then written to the memory location pointed to by out.

The buffer pointed to by in contains the byte sequence 0x31 0x32 0x33 0x34, corresponding to the ascii characters 1234, followed by twelve bytes with the value 0x0c. These trailing bytes are PKCS#7 padding added before encryption. Since the password consists of only four characters, twelve additional bytes are required to fill the final 16-byte AES block. Therefore, the padding value is 0x0c (decimal 12), repeated twelve times.

The padding is part of the encrypted data and is therefore also processed by AES; the corresponding decryption routine must validate and remove it after decrypting the ciphertext. Note that aesni_cbc_encrypt can be called multiple times depending on the password length. In this case, the password is only four characters long and fits into a single 16-byte AES block, so aesni_cbc_encrypt is called only once.

Interestingly, Oracle does not use a randomly generated initialization vector and instead, the ivec argument points to a 16-byte sequence consisting entirely of zeros (as indicated by ivec e:).

When aesni_cbc_encrypt returns, the ciphertext byte sequence in the buffer pointed to by out matches the sequence highlighted in green in the decoded base64 output shown in Listing 6. This means that the 16 bytes starting at offset 17 and ending at offset 32 (using zero-based indexing) in the decoded base64 output contain the encrypted ciphertext.

So, analysis of the function flow trace reveals that the obfuscated password value stores two components: an AES-128 encryption key and the ciphertext of the encrypted password. For deobfuscation, Oracle first extracts the embedded AES-128 encryption key (offsets 1 through 16) and uses it to decrypt the associated ciphertext (offsets 17 through 33).

There are still two details we have not covered yet. What is the meaning of the value 0x15 at offset position 0 in the decoded base64 output, and how exactly does Oracle generate the encryption key?

I do not know the exact meaning of the leading byte value 0x15, but it is a fixed value set by the ztcsh function. I strongly suspect that it represents a header or version flag. However, since the value is always constant, we do not need to consider it further for this analysis.

Having addressed the meaning of the leading byte 0x15, we can now return to the more interesting question of how Oracle generates the AES-128 encryption key. The answer can be observed in the call to RAND_bytes, another OpenSSL function that, according to the documentation (see also 8), generates num random bytes using a cryptographically secure pseudo random generator (CSPRNG) and stores them in buf.

Oracle incorporates OpenSSL functions into its libnnzsrv.so shared library. A previous post analyzing how Oracle 26ai generates UUIDs already identified this integration (see also 9). Interestingly, UUID generation and the generation of the 128-bit AES encryption key for the credential password obfuscation process both use the same internal code path (function ztcr2rnd).

In the example trace shown in Listing 7, RAND_bytes is called with num=16 and buf pointing to 0x7ffc243938c0. This means that the function generates 16 random bytes and stores them at the memory address 0x7ffc243938c0. Inspecting the 16-byte sequence at that address on function entry (buf e:) and function return (buf r:) confirms that this random byte sequence is the same 16-byte sequence later passed as the encryption key (userKey) to the aesni_set_encrypt_key function.

This shows that Oracle uses a randomly generated 128-bit AES key to transform the credential password into ciphertext, storing the key alongside the ciphertext in the resulting obfuscated value.

Additional Observations

During the investigation, I came across additional observations that are not relevant to the password obfuscation process itself, but are worth mentioning nonetheless. While they do not contribute to understanding how the password is obfuscated, they may provide useful insights or prove relevant in other contexts, perhaps in future investigations.

Besides generating a random 128-bit AES encryption key (as shown above), the obfuscation code path also invokes a function named jsciGetObfKey (not shown in the analysis above). This function concatenates the following data into a single string, suggesting that Oracle uses an additional obfuscation key.

  • DBID of the container (cdb or pdb) in which the credential is created (4093572297)
  • Credential user name (TCTEST)
  • Database unique name (DB_UQ_NAME, anonymized the example below)
  • Credential owner name (SYS)
  • OS-specific platform string (Linux x86 64-bit)

This can be observed by executing the jsciObfuscatePassword.bt script with the verbose option, which shows that the function jsciGetObfKey concatenates these values into a combined string (stored at address 0x7ffc24393970):

However, note that this “obfuscation key” string is not used in the password obfuscation process at all. Therefore, it is unclear why it is called and whether its omission from the obfuscation process is intentional or accidental. If it were used in the obfuscation process, deobfuscating a credential password would require access to the obfuscation key, and without it, it would not be possible to deobfuscate a password. The drawback would be that this would tie the obfuscation scheme to a specific database, preventing credentials from being used across different databases, for example after duplicating a database under a different name.

Password Obfuscation and Deobfuscation Step by Step

To obfuscate a credential password, Oracle constructs a buffer containing a header value, a randomly generated AES-128 encryption key, and the encrypted password ciphertext, and finally encodes the complete buffer using base64.

The individual steps are as follows:

  1. Write the constant one-byte header/flag value 0x15 to buffer offset 0
  2. Write a randomly generated AES-128 encryption key (generated by the OpenSSL RAND_bytes function) to buffer offsets 1–16
  3. Write the ciphertext produced by encrypting the plaintext with the AES-128 key stored at offsets 1–16 to buffer offset 17–end
  4. Encode the complete buffer (offsets 0–end) using base64 encoding and store the resulting base64-encoded string in sys.scheduler$_credential

To deobfuscate a credential password, Oracle reverses the steps described above:

  1. Decode the base64-encoded password string from sys.scheduler$_credential and recover the original buffer
  2. Extract the AES-128 encryption key from offsets 1–16
  3. Extract the encrypted ciphertext from offsets 17–end and decrypt it using the AES-128 bit encryption key
  4. The header/flag value at offset 0 is ignored

Obfuscation is not Encryption

Although obfuscation can make sensitive data appear unreadable, it should not be considered a replacement for encryption. Encryption protects confidentiality through the use of a secret key, whereas obfuscation merely adds a layer of obscurity without strong confidentiality guarantees. Once the obfuscation scheme is understood, the original data can typically be recovered, as demonstrated in this post.

Oracle also supports encrypting credentials stored in the data dictionary instead of using the default obfuscation mechanism. However, the encryption of credentials is not enabled by default and must be explicitly enabled. The steps required to do so are outlined in the Oracle documentation, and Oracle recommends encrypting credentials as a security best practice (see also 12).

Encryption of credentials in the data dictionary requires that the database has a keystore and an encryption key configured. Unlike other forms of encryption in Oracle, however, this does not require an Advanced Security Option license (see 12). A drawback, however, is that once an encryption key has been configured in a wallet, the wallet can no longer be removed (see also 13).
