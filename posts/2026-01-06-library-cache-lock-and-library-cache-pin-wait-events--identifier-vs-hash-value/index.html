Library Cache Lock and Library Cache Pin Wait Events — Identifier vs Hash Value

2026/01/06

This post is a follow-up note to a previous note, which explained how to decode the additional context information encoded in the P3 parameter for the library cache lock and library cache pin wait events.

To quickly recap, the P3 wait event parameter is a 64-bit (8-byte) integer value that encodes the following information (from most significant to least significant position):

  • 4 bytes (IIII) — handle identifier (note: for cursors idn, shows the hash value, not the identifier)
  • 2 bytes (NN) — namespace
  • 2 bytes (MM) — requested lock or pin mode

As casually noted in parentheses, there is a specific aspect to be aware of regarding the handle identifier idn in relation to cursors. This post explains in more detail exactly what that is. Note that all tests and results presented in this post were conducted on Oracle database version 23.26.

Various sources on the internet map the idn (“identifier”) to a library cache object’s hash value and use WHERE clauses like HASH_VALUE = &idn in queries to look up library cache object information from views such as v$db_object_cache. This approach is frequently used in combination with library cache mutex- and cursor pin-related waits, for which the P1 parameter is described as idn.

However, using the idn value to look up object information by hash value does not reliably work with library cache locks and pins, as in this context the idn value only reflects the hash value for cursor objects; for other object types, such as tables, packages, procedures, etc., the idn value differs from the hash value.

Consequently, for library cache lock and pin waits, the decoded idn value from the P3 parameter cannot be relied upon to identify the affected object, and instead, the handle address exposed in the P1 parameter should be used:

The examples below illustrate the difference between the identifier (idn) and the hash value based on library cache dumps and bpftrace output.

This first example shows a level-16 library cache object dump of the DUAL table, for which the handle address is 0x7BDDCE488:

The library cache dump excerpt shows that, for the DUAL table object in the library cache, Oracle computed a Hash value of eee30b3d (decimal 4007856957, line 15) and an Identifier value of 148 (line 19). As this mismatch illustrates, there is apparently a difference between an object’s identifier and its hash value.

However, the situation is different for cursors. The following example shows a level-16 library cache object dump, but this time a parent cursor with handle address 0x7735E6808. This is the parent cursor for a simple query against the DUAL table:

In this case, the Hash value of 8ba84e61 (decimal 2343063137, line 16) matches the Identifier value of 2343063137 (line 20). This is why using WHERE clauses like HASH_VALUE = &idn works for cursors.

💡 Tip
When using the x$ table x$kglob to look up library cache object details, parent cursors can be identified by identical parent and child handle addresses (i.e., kglhdpar = kglhdadr).

Similarly, child cursors can be identified by differing parent and child handle addresses (kglhdpar != kglhdadr).

Let’s dump the child cursor with handle address 0x757798298 next:

Interestingly, the child cursor object dump shows neither a hash nor an identifier value. This indicates that Oracle retrieves the hash value from the parent cursor. The next few paragraphs show how this can be observed using bpftrace.

Behind the scenes, Oracle uses the function kglHandleWaitPar3 to compute and encode the P3 wait event parameter, which in turn invokes several helper functions to collect additional wait event context information. Since simulating library cache lock contention takes some effort, I decided to conduct a simpler experiment by just manually invoking kglHandleWaitPar3 from gdb and tracing its execution with the bpftrace script kglHandleWaitPar3.bt, as demonstrated below.

Needless to say, this procedure is experimental and should only be performed in a lab environment.

On line 10, the kglHandleWaitPar3 function is invoked with the second and fourth argument specifying the library cache handle address of the child cursor (0x757798298) and the requested lock mode (0x2 = share mode), respectively. The first and third function arguments are not relevant, therefore supplied as 0x0. Line 11 prints the encoded P3 return value, consisting of idn, namespace, and mode.

The bpftrace output shows kglHandleWaitPar3 calling the kglHandleParent and kglHandleHash helper functions on lines 15 and 17:

  • kglHandleParent takes the child’s handle address as its second argument (0x757798298) and returns the parent handle address (0x7735e6808).

  • kglHandleHash takes the parent handle address returned by kglHandleParent (0x7735e6808) and returns the computed hash value 0x8ba84e61, which in turn is encoded into the P3 before kglHandleWaitPar3 completes.

  • kglHandleParent takes the child handle address as its second argument (0x757798298) and returns the parent handle address (0x7735e6808).

  • kglHandleHash takes the parent handle address returned by kglHandleParent (0x7735e6808) and returns the computed hash value 0x8ba84e61, which is then encoded into the P3 parameter before kglHandleWaitPar3 completes.

Compare this with a trace of kglHandleWaitPar3 when the parent cursor’s handle address 0x7735e6808 is supplied:

For a parent cursor, the behavior of kglHandleWaitPar3 slightly changes:

  • kglHandleParent doesn’t find a parent cursor (apparently, a parent cursor cannot itself have a parent), and therefore returns 0.
  • Unlike the child cursor case, kglHandleHash is not called; instead, kglHandleIdn with the parent cursor’s handle address 0x7735e6808 as the second argument (line 20), but it does not return an identifier value but rather the parent cursor’s hash value.

Finally, let’s trace kglHandleWaitPar3 for the DUAL object with handle address 0x7BDDCE488:

In this case, kglHandleWaitPar3 calls kglHandleParent, which returns 0x0 since there is no parent object, and then calls kglHandleIdn, which returns the idn value 0x94 (decimal 148).

This experiment shows that the idn value encoded in the P3 wait event parameter of the library cache lock and library cache pin wait events reflects a library cache object’s hash value only when the object is a parent or child cursor. Therefore, the idn value decoded from the P3 wait event parameter should not be used to look up library cache object details; instead, the handle address exposed in the P1 parameter should be used.

On a related note, the identifier and hash values are generated by different functions. The identifier value is computed in kgghash, whereas the hash value is generated by kglComputeHash0.
