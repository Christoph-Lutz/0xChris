Extracting Fixed View Definitions From The Oracle Binary

2026/05/19

If you’ve ever needed to look up the definition of a dynamic performance view in Oracle, also referred to as a fixed view, or simply a V$ view, chances are that you’ve come across V$FIXED_VIEW_DEFINITION.

It is a special dynamic performance view that exposes the SQL definitions of Oracle’s V$ views in its VIEW_DEFINITION column, which is defined as VARCHAR2(4000), as shown by the output of describe (from version 23.26.0.0):

The maximum size of VARCHAR2 columns in Oracle is limited to 4000 bytes (see also source 1), unless MAX_STRING_SIZE is set to EXTENDED, though this does not apply to data dictionary columns, which remain capped at 4000 bytes.

Since some V$ view definitions exceed the VARCHAR2 limit of 4000 bytes, they are truncated when queried from V$FIXED_VIEW_DEFINITION. This behavior was observed and discussed by Jonathan Lewis in this post (see also source 2), which also examines Oracle’s internal memory layout, showing that the X$ table x$kqfvt exposes a pointer-to-pointer chain that leads to the fixed view’s SQL text in memory (kqfvt likely stands for “Kernel Query Fixed tables View Text”).

Based on Jonathan’s findings, the technique I use to retrieve fixed view definitions exceeding 4000 bytes is as follows: locate the pointer to the SQL text pointer in x$kqfvt (joined to x$kqfvi for convenient lookup by view name), then follow and dereference the pointers in gdb.

To illustrate this, let’s walk through a concrete example step by step, starting with a query adapted from source [2] that returns the starting address of the pointer-to-pointer chain for the GV$SESSION view, whose definition exceeds 4000 bytes.

In this case, address 0x000000001B4F7C70 points to the start of the pointer chain. By attaching to a running Oracle process with gdb, we can follow the chain by treating address 0x000000001B4F7C70 as a double pointer (pointer to a pointer) and dereferencing it.

The gdb command x/s *(char **) 0x000000001B4F7C70 (line 5) treats the address as a char **, dereferences it to obtain the underlying string pointer, and prints the corresponding null-terminated string. By default, gdb limits the number of elements printed for arrays and strings, so the set print elements 0 command (line 3) disables output truncation. Note that I edited and shortened the SQL text output (lines 6 - 9) for readability.

I recently needed the definition of a fixed view that is longer than 4000 bytes and thought it would be useful to have a tool that could automate retrieving the full view definition. For that reason, I ended up digging deeper and wrote a small script that extracts the fixed view definitions directly from the oracle binary.

The script is called kqfvi.sh (see source 4) and is essentially a small bash wrapper around a gdb script with embedded Python logic that automates locating the internal fixed view definition structures in the oracle binary. I’ll briefly show its usage and discuss the internal structures in the next section of this note.

The script requires the ORACLE_HOME environment variable to be set and works with 19c and 26ai (I tested it with versions 19.26, 23.26.0 and 23.26.1, but have not checked other versions).

When executed without any arguments, it examines the oracle binary in the $ORACLE_HOME/bin directory and extracts the definitions of all fixed views (note that the view definitions shown in the output below are truncated for readability; the script does print the full view text).

If you are interested in the definition of a particular view, especially one that exceeds the length of 4000 bytes, like GV$SESSION, you can specify that view as an argument. While the script automates the extraction process, the interesting part is how it discovers and traverses the underlying fixed view structures inside the oracle binary. If you are interested in that kind of detail, the next section walks through the internal structures and discusses my findings along the way (as observed in version 23.26.0.0)

A Look Behind The Scenes

My investigations started with an interesting comment on Jonathan’s blog by Mikhail Velikikh (source 3), where he explains that the addresses (pointers) exposed by x$kqfvt come from the underlying structure kqfvip, which resides in the oracle binary’s read-only data (.rodata) section, as indicated by the R symbol type in the following nm output.

Structures in a binary’s .rodata section can be examined by loading the binary into gdb without the need to attach to a running process. This means we can extract the view definitions directly from the oracle binary, provided that we understand the kqfvip structure in more detail.

So, the example below loads the oracle binary (version 23.26.0.0) into gdb and examines 15 consecutive 8-byte (giant word) values in hexadecimal starting at the memory address of kqfvip.

The output reveals a pattern and shows that kqfvip appears to be an array of five 8-byte words, i.e., 5 × 8 = 40 bytes (0x28) per element. This is further illustrated by the color highlighting, which groups the memory layout into three distinct 40-byte (0x28) blocks, each corresponding to an array element.

Inspecting the individual array elements shows that the first entry in each element is a memory address pointing to the fixed view definition text (output shortened and formatted for readability).

Using this information, we can iterate over the kqfvip array and print out all fixed view definitions. There is only one missing piece: the array size. Without knowing how many elements the array contains, we don’t know when to stop.

The answer to this turns out to be stored in variable kqfvpsz, which is also stored in the oracle binary’s .rodata section and which equals 1778.

Comparing that with the number of entries in V$FIXED_VIEW_DEFINITION confirms that we are very close.

The off-by-one difference between kqfvpsz and the number of entries counted in V$FIXED_VIEW_DEFINITION is explained by a terminating zero element at the end of kqfvip. This can be seen by examining the last element using gdb (note that arrays use 0-based indexing, so the memory offset of the last element is calculated as (kqfvpsz - 1) * elem_size).

This leaves us with two options for extracting all fixed view definitions from kqfvip: either maintain a loop counter or iterate until we reach the terminator entry. Note that the underlying type structure of kqfvip is not publicly available, so we cannot use pointer arithmetic or array indexing in gdb and must instead resort to raw address calculations, which is quite messy.

Both approaches shown above print the value of the loop counter $i on every iteration. This value corresponds to the indx column in x$kqfvi and x$kqfvt, the two X$ tables that we joined together earlier to look up the pointer chain leading to the fixed view definition text.

If you’ve carefully studied the query result in Listing 14, you may have noticed that the index in x$kqfvt corresponds to the index in x$kqfvi, which is the X$ table containing the view name (exposed in column KQFVINAM). This allows us to use the index number to look up the view name, provided we know where the structure behind x$kqfvi is and how it is laid out.

As it turns out, the structure behind x$kqfvi is an array named kqfviw, which also contains 1778 elements. Examining its elements in gdb shows the following:

As illustrated by the color highlighting, each element in kqfviw consists of ten 8-byte words, i.e. 10 × 8 = 80 bytes (0x50).

For each element, the length of the view name (not including the trailing null terminator) is stored at offset 0x0, and a pointer to the view name is stored at offset 0x8; to illustrate:

Using GV$SESSION at index position 66 as an example again, we can look up its view name string in kqfviw by using the index to compute the element offset from the base of kqfviw, and then dereferencing the pointer stored at offset 0x8 within that element.

Since the index number corresponds to the element position in both arrays, it can be used as a direct mapping key to relate entries in kqfviw to their corresponding view definitions in kqfvip. To locate a view by name, a simple linear scan over the kqfviw array can be performed: each element is inspected and the view name pointer at offset +0x8 is compared against the target name. Once a match is found, the current index position is reused to access the corresponding entry in kqfvip, thereby retrieving the associated view definition — this is precisely the approach used in the script kqfvi.sh does.
