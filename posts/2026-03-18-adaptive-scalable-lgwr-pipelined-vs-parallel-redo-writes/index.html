Adaptive Scalable LGWR Pipelined vs Parallel Redo Writes

2026/03/18

An earlier post explained the decision-making heuristics when LGWR transitions from single to scalable mode. Here, we examine how it handles redo writes in scalable mode with multiple LG worker processes. Note that all observations are based on Oracle 19.26 with Exadata software 25.2.6, but as Oracle’s internal LGWR mechanics are not publicly documented, behavior may change or vary in other versions.

In scalable mode, LGWR can assign redo writes to multiple LG worker processes in the following ways:

  • Parallel writes: Multiple LGWR worker processes (LGnn) cooperate on the same redo write in parallel. The maximum number of workers that can participate in a single redo write is determined by _max_log_write_parallelism.

  • Pipelined (overlapped) writes: Multiple LG worker groups process different redo writes concurrently. The maximum number of outstanding redo writes is determined by _max_outstanding_log_writes.

  • Pipelined (overlapped) parallel writes: A combination of both mechanisms; that is, multiple worker groups process different redo writes concurrently, and each individual redo write is processed in parallel by multiple LG worker processes.

Note: Strictly speaking, LGWR always assigns a redo write to a worker group, which consists of one or more LG worker processes. However, in this post, I use the terms “worker group” and “LG worker” somewhat loosely and interchangeably.

The figures below graphically illustrate how LGWR can assign a redo write to multiple workers:

It is important to note that LGWR first collects (“gathers”) the redo buffers from the active public redo strands, organizes them into a batch of work, and then assigns an LWN to that batch before distributing the work to worker processes.

The official meaning of LWN is not publicly documented by Oracle. However, investigations by Frits Hoogland describe it as a “Log Write Number”, which identifies a batch of redo buffers to be flushed to disk by LGWR (see also 1 and [2]).

LGWR increments the LWN for every redo write and also tracks an associated LWN SCN. Since LGWR can split a batch of work and assign portions to different worker processes (which may then further split the redo write into multiple physical I/O requests at the syscall layer), you can also think of the LWN as a “Logical Write Number”.

With the fundamentals outlined, let’s examine the following questions:

  1. What is the default redo write mode when LGWR operates in scalable mode — pipelined or parallel?
  2. How does LGWR decide whether to pipeline (overlap) or parallelize a redo write?
  3. How can we observe LGWR’s redo write behavior in scalable mode?

The short answer to the first question is that, in scalable mode, LGWR uses pipelined writes by default and performs parallel writes only when specific conditions are met.

The following conditions determine whether LGWR assigns a redo write to multiple LG workers for parallel processing:

  • The size of the redo write must exceed the maximum I/O size defined by _max_io_size, which is 1 MB (1048576 bytes) on most platforms. Internally, Oracle evaluates the redo write size in redo blocks, meaning LGWR checks whether the redo write size exceeds 2048 redo blocks (assuming a redo block size of 512 bytes, since 2048 x 512 bytes = 1MB); therefore, the condition is: redo write size > 1 MB.

  • There must be more than one active public redo strand. Note that Oracle only activates additional public redo strands when there is pressure on the redo allocation latches (the exact activation mechanics are a topic for another post). Internally, the number of active public redo strands is tracked in the SGA variable kcrf_actv_strands_, so the condition is kcrf_actv_strands_ > 1.

  • _max_log_write_parallelism must be greater than 1. This may appear obvious, but keep in mind that on Exadata X8M and X9M systems using the PMEM log feature, Oracle automatically sets _max_log_write_parallelism=1, which effectively disables parallel redo writes on these systems (see also [3] for further information on how Oracle adjusts _max_log_write_parallelism on Exadata X8M and X9M).

strands_per_worker represents the number of public redo strands assigned to each worker, assuming all strands are active and evenly distributed across the maximum number of workers allowed to process a redo write in parallel.

active_strands is the number of active public redo strands, derived from the highest active strand number. Since strand numbering starts at 0, the number of active strands is equal to the highest active strand number plus one.

workers determines how many workers are assigned to process a redo write in parallel, considering all currently active strands (represented by highest_actv_strand + 1) and assuming each worker processes up to strands_per_worker strands.

To summarize, in scalable mode, LGWR uses multiple LG worker processes to process a redo write in parallel only when more than one public redo strand is active, the redo write size exceeds 1 MB (2,048 redo blocks of 512 bytes), and _max_log_write_parallelism is greater than 1. If any of these conditions is not met, LGWR uses pipelined redo writes instead.

While Oracle’s scalable LGWR design improves redo write throughput, it also introduces certain architectural trade-offs and drawbacks:

Recovery must ensure that redo log entries are applied in LWN order. However, the change records in an LWN batch are not ordered in SCN order, and therefore, recovery must first sort and order all change records in an LWN batch by SCN (change records in an LWN are only partially ordered, since every public redo strand maintains SCN order, but there is no guaranteed global SCN order across strands).

Worker coordination and synchronization: Pipelined redo writes allow a new logical write (LWN batch) to begin before a previous logical write completes. Therefore, a logical redo write with a higher LWN may complete before a redo write with a lower LWN; in other words, write ordering is not guaranteed for pipelined redo writes submitted consecutively to different LG workers. Similarly, there is no guaranteed write ordering for different portions of a redo write processed by multiple workers in parallel, and they may reach the storage subsystem in an order different from the logical sequence of the original redo buffers.

This means LGWR must coordinate and synchronize redo writes between worker groups, and worker groups must coordinate and synchronize the workers within their group (which explains the various LGWR inter-group and intra-group wait events in Oracle, though these are a topic for another post). If, for instance, a second logical write completes before a first logical write, Oracle cannot advance the on-disk SCN and notify committing sessions to proceed while the first write is incomplete, as this would leave holes in the redo log in the event of an instance crash (all change records with an SCN lower than the on-disk SCN are guaranteed to be written to disk). Synchronization must therefore enforce ordered updates to the on-disk SCN to guarantee transactional correctness.

Write size variation and pipeline stalls: If pipelined log writes vary significantly in size, the likelihood increases that smaller, subsequent logical writes complete before a larger, preceding one. If, for instance, a large amount of redo data has accumulated in the log buffer, LGWR assigns a large logical write to a worker. If a second write request arrives shortly after, the accumulated data in the log buffer may be much smaller, resulting in a smaller logical write that is very likely to complete before the earlier logical write processing a larger amount of redo. As explained in the previous paragraph, such situations require coordination to guarantee transactional correctness, so variations in write size can cause stalls in the write pipeline, severely limiting redo write throughput.

The following diagram provides a graphical illustration of the problem:

In this example, five chunks of redo data reside in the redo log buffer and LGWR pipelines these chunks so they are written by workers LG00, LG01, LG02, LG03, and LG04 in an overlapping manner. Write 1, processed by LG00, is a large write that incurs high latency. As a result, the smaller writes processed by the remaining workers (Write 2, Write 3, Write 4, and Write 5) all complete before Write 1.

This situation stalls the LGWR write pipeline, since LGWR cannot assign new logical writes to LG01, LG02, LG03, or LG04 until LG00 has completed the large write and updated the on-disk SCN (indicated by “S” in the diagram). Consequently, LG01, LG02, LG03, and LG04 remain unavailable for new logical writes, severely limiting redo write throughput and thereby increasing commit latency for foreground (FG) processes.

📝 Exadata Pipelined Log Writes

On Exadata models X10M and newer, Oracle addresses pipeline stalls with the Pipelined Log Writes feature, introduced with Oracle 19.22+, Oracle 26ai, and Exadata System Software release 24.1.0 and newer. The marketing name is somewhat misleading, since LGWR has been performing pipelined writes in scalable mode for a long time.

The new Exadata-only feature would be more accurately called “Pipelined Log Writes with Size Regulation,” since LGWR no longer unconditionally pipelines new logical writes to workers, but only allows a new write if any of the following conditions are met:

  1. No logical write is currently in progress.
  2. The size of a new logical write meets a minimum write size threshold (dynamically computed by LGWR at runtime).
  3. A timeout is reached while waiting for a logical write to meet the size threshold (the timeout threshold is also dynamically computed by LGWR at runtime).

If neither of these conditions is met, LGWR defers the logical write and actively spins on the CPU (busy looping) until either a sufficiently large write size accumulates in the redo log buffer or the timeout expires.

LGWR dynamically tunes the write size threshold at runtime based on redo workload demands. Under light and moderate redo load, it aims to optimize commit latency by maintaining a small and consistent redo write size while distributing logical writes across as many workers as possible. Once all workers are busy, LGWR begins to step-wise increase the redo write size, optimizing for redo write throughput at the expense of commit latency.

The timeout threshold acts as a deadline to maintain reasonable commit latency when insufficient redo data accumulates in the redo log buffer to meet the write size threshold. The detailed mechanics and threshold calculation formulas are a topic for another post, though.

Interestingly, Oracle provides no instrumentation to indicate whether a redo write is processed in pipelined or parallel manner. So, we need to develop our own, and bpftrace is the perfect tool for this kind of job. However, in order to observe pipelined and parallel redo writes accurately, we need to first understand the low-level mechanism and kernel functions LGWR uses to assign redo writes to multiple workers.

Behind the scenes, LGWR calls the Oracle kernel function kcrfw_slave_queue_insert to assign redo write tasks to worker processes in scalable mode (kcrfw = Kernel Cache Recovery File Write). The function takes eight arguments, of which only the last three are relevant to our analysis (arg5, arg6, and arg7, named lwn_scn_p, workers, and pic, respectively):

The arguments have the following meanings (based on my understanding, as these are not necessarily the names used in the Oracle source code):

  • lwn_scn_p (arg5): Pointer (on the stack) referencing the LWN SCN
  • workers (arg6): The number of LG workers assigned to work on a redo write in parallel
  • pic (arg7): Pointer to a pending I/O context, an internal structure used by LGWR to track redo write requests and their status

The workers parameter shows the number of workers assigned to process a logical write. When set to 1 in scalable mode, LGWR issues a pipelined write; when set to a value greater than 1, it issues a parallel write. The other parameters provide additional context information, but are not relevant here, as the value of the workers parameter alone is sufficient to determine whether LGWR issues a pipelined or a parallel redo write. We can read its runtime value using bpftrace with a uprobe on function kcrfw_slave_queue_insert, as shown below:

When the uprobe fires, it retrieves the workers argument (arg6) from the stack at offset %rsp + 0x8 (lines 8-9). The reason is that in the x86-64 calling convention, only the first six arguments (arg0 – arg5) are passed via registers; remaining arguments (arg6 and beyond) are passed on the stack. Once retrieved, the workers value is stored in a bpftrace linear histogram called @workers_hist (line 10). This histogram displays the distribution of workers with buckets ranging from 0 to 16 in steps of 1.

If you want to try the script yourself, note that it accesses raw memory addresses in the SGA, which are not stable and may change across Oracle RUs. Therefore, if you are using an Oracle version other than 19.26, it may not function correctly.
