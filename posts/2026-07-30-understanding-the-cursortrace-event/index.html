Understanding the CURSORTRACE Event

2026/07/30

The Oracle library cache is extensively instrumented, but the instrumentation is disabled by default. It can be enabled using the CURSORTRACE event, which is particularly useful for investigating library cache problems, especially cursor sharing issues related to child cursor mismatches, high version counts, or unexpected hard parses. Beyond troubleshooting, the CURSORTRACE event also provides valuable insights into the internal behavior of the library cache, as explored in this post (see also 1).

Note that all examples, observations, and results in this post are based on Oracle release 23.26.0. If you are not interested in the implementation details of the CURSORTRACE event, you may jump directly to the practical examples section.

The exact behavior of the CURSORTRACE event is not publicly documented and is therefore likely to change across Oracle releases. Moreover, past bugs have been reported that could prevent tracing from being disabled (see also 2 and 3), so use this trace event at your own risk, and thoroughly test it on a non-production system before enabling it in production.

Note that the level and address values in the event syntax can be specified either as decimal or hexadecimal numbers. In this post, hexadecimal notation is used throughout because it makes the individual trace level bits easier to identify and combine.

The CURSORTRACE event and its trace levels are only partially documented, and My Oracle Support note KB829509 provides a good starting point (see also 4). The note describes the following trace levels and explains that different trace levels can be combined by summing their values; for instance, trace level 812 is the sum of trace levels 4 + 8 + 32 + 256 + 512.

In this post, the terms trace level and trace flag are used interchangeably. Technically, the CURSORTRACE event accepts a trace level value, which is a bit mask composed of individual trace flags. For simplicity, I use both terms depending on the context.

The note further explains that the address clause must be set to the sql hash value (V$SQL.HASH_VALUE) of the cursor to be traced. However, the example provided in the note uses the non-existent hash value 1 in the address clause, which effectively enables tracing for all statements:

It is worth noting that the trace level 812 used in the example includes level 32 (0x20), which enables tracing globally. As a result, the example effectively traces all statements executed by all sessions.

Unfortunately, there is no public documentation describing how the CURSORTRACE event behaves when enabled with different combinations of scope (global vs. local) and granularity (all statements vs. individual statements). This post aims to fill this gap by exploring different CURSORTRACE event settings at different scopes and analyzing their behavior behind the scenes.

CURSORTRACE Event Scopes and Statement Level Granularity

The following table provides a summary of the different CURSORTRACE event scopes, statement level granularity options, and the contexts in which they apply.

Scope Granularity Context
Local All statements Current session
Local Specific statement(s) Current session
Global All statements Instance-wide; applies to all pdbs when enabled in cdb$root, and only to the current pdb when enabled within a pdb.
Global Specific statement(s) Instance-wide; applies to all pdbs when enabled in cdb$root, and only to the current pdb when enabled within a pdb.
Table 1: CURSORTRACE event scope and statement granularity

The local scope applies only to the current session and can be configured to either trace all statements executed in that session or select individual statements for tracing based on their cursor hash value. However, the list of cursors in the local scope is limited to a maximum of three entries, as we will see shortly.

The global scope applies instance-wide to all sessions, but the behavior depends on whether the tracing is enabled at cdb or pdb level: if enabled at cdb level, the global scope applies to all sessions in cdb$root and all pdbs. When enabled in a pdb, the global scope only applies to all sessions within that pdb.

Interestingly, once the CURSORTRACE event has been enabled in a pdb, trace settings at the cdb level no longer propagate to that pdb. In other words, once you enable tracing at pdb level, the pdb no longer inherits subsequent CURSORTRACE trace setting changes made at the cdb level until the instance is restarted.

Similar to the local scope, the global scope also allows tracing all statements or selected individual statements based on their cursor hash value. However, the list of cursors in the global scope is also limited to three entries.

A Look Behind the Scenes

To support tracing at different scopes and levels of granularity, Oracle maintains the various internal CURSORTRACE structures:

Local scope:

  1. Session-specific trace flag for tracing all cursors in the current session
  2. Session-specific trace list (hash table) for tracing individual cursors in the current session

Global scope:

  1. Cdb-specific trace flag for tracing all cursors across the entire container database (cdb$root and all pdbs)
  2. Cdb-specific trace list (hash table) for tracing individual cursors across the entire container database
  3. Pdb-specific trace flag for tracing all cursors within a pdb
  4. Pdb-specific trace list (hash table) for tracing individual cursors within a pdb

The local and global trace flags used by Oracle to trace all cursors (items 1, 3, and 5 in the list above) are not exposed anywhere. However, the local and global trace lists used to trace individual cursors (items 2, 4, and 6 in the list above) can be dumped using the undocumented CURSORTRACE level 0xffffffff, as shown below. Note that it doesn’t matter whether you dump the trace lists using ALTER SYSTEM or ALTER SESSION, the resulting output is the same in both cases.

The trace output varies depending on whether the dump is generated from cdb$root or from within a pdb. When the dump is generated from cdb$root, it includes the global cursor trace lists for cdb$root and for every pdb in which the CURSORTRACE event has been enabled at least once (technically, every pdb in which the global CURSORTRACE hash table structure has been initialized). When the dump is generated from within a pdb, the output contains only the cursor trace list for that pdb.

As mentioned earlier, the dump generated by the CURSORTRACE event at trace level 0xffffffff includes only the global and local cursor trace lists used to trace individual cursors. It does not include the global trace flags that control tracing for all cursors.

The bpftrace script enables a systematic analysis of how the different CURSORTRACE event levels modify the global and local event structures. This provides detailed insights into the behavior of the following particularly interesting trace levels (see also Listing 2):

  • 0x10: trace locally (session-level)
  • 0x20: trace globally (cdb and pdb level)
  • 0x40: add a cursor to list to be traced
  • 0x80: remove a cursor from list to be traced
  • 0x80000000: clear and disable all tracing

Investigating the CURSORTRACE Behavior

Let’s start the investigation by observing what happens behind the scenes when enabling the CURSORTRACE event at local scope (session level). For this test, we use trace level 0x1, which is the most basic trace level (“debug level 1”). Note that we do not specify a valid sql hash value in the address clause but instead use the value 0, so this enables tracing for all statements executed in the current session.

The resulting bpftrace output shows that the local flag that controls tracing of all statements (flg_all) changes from 0x0 to 0x1 (line 13).

Dumping the CURSORTRACE event settings from the current session only shows the global and local cursor trace lists. Since we have not modified these lists, all entries are set to 0. Note that the CURSORTRACE event dump does not expose the flg_all value.

To disable tracing of all statements executed in the current session, we set the CURSORTRACE event to trace level 0x0.

The resulting bpftrace output confirms that flg_all changes from 0x1 to 0x0:

According to Listing 2, there is a local trace flag with the value 0x10. When we combine this flag with trace level 0x1 and use the ALTER SESSION command to set the resulting trace level 0x11 (0x1 + 0x10=0x11), we get the same result as in Listing 11. Similarly, if we specify trace level 0x10with theALTER SESSION` command, Oracle disables tracing of all statements in the current session and we see the same result as shown in Listing 14.

Interestingly, if trace level 0x11 is enabled with the ALTER SYSTEM rather than the ALTER SESSION command, the effect is a bit unexpected: instead of being limited to the current session, tracing is also enabled globally. As a result, the CURSORTRACE event becomes active system-wide and affects every statement executed by all sessions.

This effect can be observed in the following bpftrace output, which shows that setting the CURSORTRACE event level to 0x11 with ALTER SYSTEM changes both the local and global flg_all values from 0x0 to 0x1:

The unexpected behavior can be disabled by setting the local trace level 0x10 with ALTER SYSTEM. This resets both the local and global flg_all values back to 0x0, thereby disabling global and local tracing:

Oracle Multitenant brings yet another surprise. If trace level 0x11 is set with ALTER SYSTEM after switching from cdb$root into a pdb, Oracle not only changes the local flg_all value, but also allocates a new pdb-specific ht_gbl structure.

The bpftrace example output below demonstrates this behavior: for con_id 4, the ht_gbl address changes from 0x0701a8238 to 0x78c9aa8f8. Since the flg_all value is stored in the first four bytes of the ht_gbl structure, changing the ht_gbl structure also changes the scope of flg_all. As a result, the tracing flag is no longer cdb-wide but becomes specific to that pdb. In other words, the global tracing scope effectively moves from the cdb level to the pdb level.

After switching back to cdb$root and dumping the CURSORTRACE settings using trace level 0xffffffff, we can see that the pdb-level flg_all value differs from the cdb-level value. Consequently, in this situation, the CURSORTRACE event is enabled at level 0x1 both for the local session and for all sessions in pdb01 (con_id 4), but not for sessions connected to cdb$root.

Setting trace level 0x10 with ALTER SYSTEM from cdb$root only resets the flg_all value for the local session, but not the one for pdb01 (con_id 4):

To reset the pdb-specific flg_all value, we must switch back to pdb01 and set trace level 0x10 with the ALTER SYSTEM command. This changes the flg_all value for con_id 4 from 0x1 to 0x0, but it doesn’t restore the original ht_gbl address (which remains set to 0x78c9aa8f8).

Switching back to cdb$root and setting trace level 0x11 again with ALTER SYSTEM, changes the flg_all value in the local session and at the cdb-level, but it no longer changes the flg_all value for pdb01 (con_id 4). This means that global container-wide tracing will no longer include pdb01 (until the pdb or instance is restarted):

Note that the CURSORTRACE dump output provides no signs or indications whatsoever of this rather surprising behavior. It only shows the global and local hash tables that we are going to investigate in the next section:

In conclusion, it is best to avoid using the local trace flag 0x10 with ALTER SYSTEM, as it can lead to unexpected and non-intuitive behavior.

Let’s continue the investigation by tracing a specific statement in the current session. As an example, we trace the select sysdate statement, which has the cursor hash value 0xb16f46be:

Tracing for individual statements can be enabled using either the ALTER SESSION or ALTER SYSTEM command. With ALTER SESSION, Oracle defaults to local scope, so the local trace flag 0x10 does not need to be specified explicitly. With ALTER SYSTEM, however, Oracle defaults to global scope, requiring the local trace flag 0x10 to be specified explicitly when local tracing is intended.

Trace level with ALTER SESSION:

  • 0x01: enable debug level 1
  • 0x40: add cursor to be traced to local hash table

Trace level with ALTER SYSTEM:

  • 0x01: enable debug level 1
  • 0x10: trace locally (session-level)
  • 0x40: add cursor to be traced to local hash table

Note that with ALTER SYSTEM, the global scope applies either to the entire container when executed in cdb$root or only to the current pdb when executed within a pdb, as described in the previous section.

For the example discussed here, we use ALTER SESSION and therefore set the trace level to 0x41 (the combination of trace levels 0x01 and 0x40). The cursor hash value 0xb16f46be is specified in the address clause.

After executing this command, the following bpftrace output shows how Oracle processes the request: it increments the counter ht_cnt for the local hash table by one, adds the hash value 0xb16f46be to the third slot in the local hash table, and changes the cursor-specific trace flag (flg) value from 0x0 to 0x1. The reason flg is set to 0x1 rather than 0x41 is that the kksCursorTrace function masks out trace flag 0x40.

With this setting, Oracle traces all executions of the cursor with the hash value 0xb16f46be in the current session. After executing the second ALTER SESSION statement from the listing below, the bpftrace output shows that the local hash table now contains three entries (ht_cnt=3), all hash table slots are occupied, and the flg value of each cursor is set to 0x1.

Since the local and global hash tables have a hardcoded maximum limit of three slots, this raises the question of what happens when local scope tracing with level 0x41 is enabled for a fourth cursor.

Let’s test this by enabling tracing for the cursor select sysdate + 3, which has the hash value 0xf3c06d9a and maps to hash table position 3. In this case, the number of hash table entries remains at 3 (ht_cnt=3), but Oracle replaces the existing entry containing hash value 0x0b16f46be with the new hash value 0xf3c06d9a. As a result, the CURSORTRACE event will no longer trace the select sysdate statement (hash value 0xb16f46be) in the local session, but will instead trace select sysdate + 3 (hash value 0xf3c06d9a).

While it is useful to know that the CURSORTRACE event can be enabled for up to three different cursors, each with its own trace level, it remains unclear why this limit is hardcoded to three and why existing entries can be overwritten.

The limitation of this design becomes apparent when tracing multiple cursors. Before enabling tracing, we must carefully determine each cursor’s slot in the hash table based on its hash value; otherwise, existing entries may be overwritten. If multiple cursor hash values map to the same hash table slot, it is not possible to trace all of them simultaneously. Note that the global hash table exhibits the same behavior.

Existing cursor entries can be removed from the hash table when they are no longer needed. This can be done using trace level 0x80 together with the cursor’s hash value in the address clause. For example, to remove the first hash table entry with the hash value 0x25064a87, execute the ALTER SESSION command shown below.

The bpftrace output shows that the number of entries in the local hash table is decremented by one (ht_cnt is set to 2) and that the first hash table entry is deleted (its hash and flg values are both reset to 0).

The other two entries can be deleted in a similar way by specifying the corresponding cursor’s hash value in the address clause. Here again, when using trace level 0x80 with the ALTER SESSION command, Oracle assumes local scope and clears the local hash table, whereas with ALTER SYSTEM it assumes global scope and clears the global hash table.

However, this behavior can be overriden. For example, the ALTER SYSTEM command can be used to clear the local hash table by specifying trace level 0x90 (a combination of trace levels 0x10 and 0x80). Conversely, the ALTER SESSION command can be used to clear the global hash table by specifying trace level 0xa0 (a combination of trace levels 0x20 and 0x80). As outlined in the previous section, this behavior can be quite confusing, especially since ALTER SYSTEM executed from within a pdb has a global scope that is limited to the current pdb. Therefore, it is best to always use ALTER SESSION for local scope and ALTER SYSTEM for global scope rather than mixing the two.

Alternatively, the CURSORTRACE level 0x80000000 removes all entries from the global and local hash tables at once. However, doing so results in another unexpected behavior that appears to be a bug.

The bpftrace output below shows that setting trace level 0x80000000 clears all existing entries from the local hash table, but leaves the hash table entry counter ht_cnt unchanged at 2 (since the local hash table contained two entries before trace level 0x80000000 was set).

This has the following undesired side effect: sessions use the function kksCheckForTrace to determine which CURSORTRACE level is enabled. The function’s trace-level evaluation logic checks the global hash table only when the local hash table does not contain any entries (that is, when the local ht_cnt is set to 0). In other words, as long as any entries are (seemingly) present in the local hash table, the global hash table is ignored. Consequently, if you add a cursor to the global hash table for tracing after clearing the local hash table with trace level 0x80000000, that cursor will not be traced, even though it is globally flagged for tracing.

The global hash table exhibits the same behavior when trace level 0x80000000 is used to clear its entries: the global ht_cnt counter is not reset. This results in another side effect: the evaluation logic in kksCheckForTrace only checks whether tracing for all statements in the current session is enabled when the global hash table contains no entries (that is, when ht_cnt is set to 0). So, as long as any entries (seemingly) exist in the global hash table, the session’s trace-all flag flg_all is ignored. Consequently, if you enable session-wide tracing after clearing the global hash table with trace level 0x80000000, no statements will be traced.

To avoid side effects, it is best not to use trace level 0x80000000 for clearing cursors from the local and global hash tables, but rather delete them one by one.

Tracing at global scope (all statements or individual statements) exhibits similar quirks to those observed in the investigation above, which focused primarily on local scope. I will therefore not cover global scope behavior in further detail. Instead, the table below summarizes selected trace level combinations when used with ALTER SESSION and ALTER SYSTEM; exploring additional combinations and their behavior is left as an exercise for curious readers.

Trace Level(s) Used with ALTER SESSION Used with ALTER SYSTEM
0x10 Sets the local trace-all flag (flg_all). This enables tracing for the current session. Sets the local and global trace-all flags (flg_all). This enables tracing for the current session and globally.
0x20 Sets the local and global trace-all flags (flg_all). This enables tracing for the current session and globally. Sets the global trace-all flag (flg_all). This enables tracing globally.
0x40 Adds the cursor hash value specified by address to the local hash table. Adds the cursor hash value specified by address to the global hash table.
0x80 Removes the cursor hash value specified by address from the local hash table. Removes the cursor hash value specified by address from the global hash table.
0x10 + 0x40 Adds the cursor hash value specified by address to the local hash table. Adds the cursor hash value specified by address to the local and the global hash table.
0x20 + 0x40 Adds the cursor hash value specified by address to the local and global hash table. Adds the cursor hash value specified by address to the global hash table.
0x10 + 0x80 Removes the cursor hash value specified by address from the local hash table. Removes the cursor hash value specified by address from the local and the global hash table.

Practical Examples

As general guidelines for using the CURSORTRACE event, consider the following recommendations:

  1. Global vs. local scope
    Decide whether tracing should apply globally or locally. For global tracing, determine whether it should be enabled container-wide (affecting the cdb$root and all pdbs) or only within a specific pdb. To enable container-wide tracing, enable the CURSORTRACE event from cdb$root; for pdb-specific tracing, switch to the target pdb before enabling the event. Keep in mind that once tracing has been enabled in a pdb, the CURSORTRACE event settings no longer propagate from cdb$root to that pdb until that pdb or the database instance is restarted.

  2. Trace all statements vs. individual statements
    Unless necessary, avoid adding multiple statements to the global or local hash table. If you decide to trace multiple statements, manually compute their hash table slots from the cursor hash values (see Listing 25) to avoid unexpected overwrites caused by hash collisions.

  3. Trace levels Combine the necessary trace levels (as shown in Listing 2), but avoid using trace level 0x20 (global scope) with ALTER SESSION, and similarly, avoid using trace level 0x10 (local scope) with ALTER SYSTEM.

  4. Removing and clearing hash table entries
    Do not use event level 0x80000000 to clear the global and local hash tables. Instead, remove hash table entries individually using trace flag 0x80.
