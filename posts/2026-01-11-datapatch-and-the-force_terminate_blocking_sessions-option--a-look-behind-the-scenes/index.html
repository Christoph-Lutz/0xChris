Datapatch And The “force_terminate_blocking_sessions” Option — A Look Behind The Scenes

2026/01/11

If you’ve ever executed Datapatch on a busy system, chances are you’ve experienced intermittent delays or hangs, and in some situations maybe even errors such as ORA-4021 (“timeout occurred while waiting to lock object”) or ORA-4020 (“deadlock detected while trying to lock object”). In many cases, this is caused by concurrent modifications to database objects (tables, views, packages, etc.) while they are being accessed by other sessions (see also 1).

For that reason, Oracle recently announced support for a new Datapatch “kill switch” that attempts to address these kinds of problems by automatically killing blockers that get in the way of Datapatch (see 2 and 3).

This new option is named force_terminate_blocking_sessions, and MOS knowledge article KB148594 explains the following (see 2):

force_terminate_blocking_sessions

In Oracle databases, the Kernel Global Lock (KGL) in exclusive (X) mode is used to manage library cache objects, such as SQL statements and PL/SQL procedures. At times, sessions may block each other due to these locks, which can prevent critical operations like schema changes or object recompilation.

When you use the force_terminate_blocking_sessions option with Datapatch, it instructs catcon to terminate any session currently holding the requested KGL X lock, using the kill_kgl_x_blocker flag.

Note that there is no “Kernel Global Lock” in Oracle. Instead, KGL stands for Kernel Generic Library cache and refers to the Oracle C module kgl.c, which implements the library cache.

Objects in the library cache are protected by a two-tier locking mechanism consisting of library cache locks and library cache pins. At a high level, library cache locks are used to control access to an object and its dependencies, while pins keep objects in memory during use. This dual mechanism exists to allow as much fine-grained and concurrent access as possible.

Locks and pins can be acquired in different modes, which may not be compatible with each other (see MOS KB830534 for a compatibility matrix). If this occurs, sessions must wait until the requested lock or pin is granted, or until the timeout defined by _kgl_time_to_wait_for_locks expires (it defaults to 15 minutes in 19c and 26ai, and sessions raise an ORA-4021 error if it expires).

This is why Datapatch can occasionally hang when other sessions hold incompatible locks or pins during patching. I was therefore wondering how the new force_terminate_blocking_sessions option works behind the scenes, and how Datapatch would detect and kill blocking sessions.

Knowing these parameters is useful, because it allows us to tweak them systematically and observe their effects. Let’s start with a simple baseline test to establish expected behavior before making any changes in the new parameters.

In the following test, session 1 invokes the dbms_lock.sleep procedure to sleep for three minutes. The second session then attempts to compile the dbms_lock package, setting _kgl_time_to_wait_for_locks to one minute so that the lock/pin acquisition timeout expires before the sleep in session 1 completes (with the default settings, the timeout would expire after 15 minutes).

The call to dbms_lock.sleep causes session 1 to pin the dbms_lock object in the library cache in share mode (S). This is not compatible with the pin request in exclusive mode (X) from session 2, which is needed to recompile the object. As a result, session 2 must wait and raises an ORA-4021 error after one minute, when the lock acquisition timeout expires (_kgl_time_to_wait_for_locks=1).

Let’s repeat the test, but this time with _kgl_kill_final_blocker=true at session level, similar to what Datapatch does when the force_terminate_blocking_sessions is used.

The first session terminates with an ORA-3113 error after about two minutes, which matches the default two-minute setting of _kgl_final_blocker_kill_begin_time. The package compilation in session 2 also completes after about two minutes, because its exclusive-mode library cache pin request can be granted once session 1 has terminated.

With _kgl_final_blocker_kill_begin_time=1 set in the second session, the first session terminates after one minute (not shown). Note that one minute is the minimum value for this parameter and values lower than one minute are not possible.

Interestingly, if _kgl_final_blocker_kill_begin_time and _kgl_time_to_wait_for_locks are set to the same value, the lock acquisition timeout appears to take precedence, and the second session fails with an ORA-4021 error. However, I haven’t investigated this case in great detail, so I don’t know whether this behavior is deterministic or caused by specific conditions in my test environment.

In the background, the process executing the waiting session (session 2 in the examples above) uses the tgkill and rt_tgsigqueueinfo system calls to send two signals to the blocker, as shown in the following strace output:

First, the blocked process sends a SIGTSTP to the blocker (pid 291220) using tgkill, suspending the blocker’s execution (line 3). Next, it sends a SIGTERM using rt_tsigqueueinfo, requesting the blocker to terminate (line 22). Unlike the SIGKILL signal (kill -9), SIGTERM politely asks a process to stop running, giving it a chance to clean up resources, close files, and release locks before terminating. Interestingly, Oracle doesn’t use the kill system call to deliver signals to the blocker, but instead uses tgkill and rt_tsigqueueinfo, which allow targeting specific threads and, in the case of rt_tsigqueueinfo, also passing additional signal information in a thread-safe manner. This is likely because Oracle introduced support for a multithreaded execution model back in Oracle 12c.

The stack traces also nicely illustrate how execution flows through the various Oracle kernel layers. In this case, the library cache pin is requested and allocated in the library cache functions kglpin and kglpnal, but since it’s held in an incompatible mode by session 1, the library cache determines the final blocker (function kglFinalBlocker) and then calls into the kernel services layer (ks), requesting termination of the blocker using a VOS-specific handler function (vos = virtual operating system layer; function names are usually prefixed by s).

Before closing, here are some observations and remarks about the underscore parameters _kgl_max_wait_time_during_kill and _kgl_4021_assert_on_oso.

In my tests, changes to parameter _kgl_max_wait_time_during_kill did not result in any observable behavior changes, even when constructing more complex hang scenarios and multi-level hang chains.

The parameter _kgl_4021_assert_on_oso slightly changes the ORA-4021 error behavior when an Oracle supplied object is involved (Oracle supplied objects are objects for which dba_objects.oracle_maintained shows Y). Usually, ORA-4021 errors are not logged to the alert log, but when _kgl_4021_assert_on_oso is enabled at session level, a session encountering an ORA-4021 on an Oracle supplied object, will create an indicent trace file and emit an alert log entry like the following:

The ORA-700 error arguments expose the following detail information:

  • arg1: ORA-4021
  • arg2: the object owner
  • arg3: the object name
  • arg4: lock or pin (in this case a pin)
  • arg5: kgl handle address (x$kglob.kglhdradr)
  • arg6: lock or pin address (x$kgllk.kgllkadr or x$kglpn.kglpnadr)

I assume Datapatch enables _kgl_4021_assert_on_oso when the force_terminate_blocking_sessions option is used, to make ORA-4021 errors on Oracle supplied objects during patching visible in the alert log (wrapped in ORA-700 soft errors).

Summary

The Datapatch option force_terminate_blocking_sessions is essentially just a flag that makes Datapatch set the two undocumented parameters _kgl_kill_final_blocker=true and _kgl_4021_assert_on_oso=true at session level. The first setting enables a new library cache kill facility introduced in 21c, and the second logs ORA-4021 errors to the alert log when a library cache lock or pin request for an Oracle-supplied object runs into a timeout. Since this is not a Datapatch feature but rather a generic RDBMS capability, it could also be used in other scenarios not involving Datapatch.

With the default settings, a session waiting for a library cache lock or pin will send a kill (using SIGTERM) to the blocker process after a timeout of 2 minutes, as defined by _kgl_time_to_wait_for_locks. When changing this parameter, ensure that _kgl_time_to_wait_for_locks is set to a value greater than _kgl_max_wait_time_during_kill; otherwise you may encounter ORA-4021 errors before a blocked session begins terminating the blocker.

This note just covered very basic hang scenarios, and all observations and test results are from Oracle 26ai (23.26) in a single-instance, non-RAC environment (cluster_database=false). The reason for mentioning the single-instance configuration is that KGL kill behavior changes on RAC, because library cache locks and pins are global resources managed by the Global Enqueue Service (GES). These RAC effects are especially pronounced in more complex hang scenarios and hang chains involving multiple sessions stuck in library cache lock and pin waits. However, this is something to be covered in more detail in a follow-up note.
