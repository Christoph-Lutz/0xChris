Deobfuscating Auto-Login Wallets in Oracle 26ai

2026/08/31

After looking into how Oracle obfuscates credential passwords and database link passwords in version 26ai (see also 1 and 2), I started wondering how auto-login wallets are obfuscated and whether the obfuscation has changed in 26ai as well.

Prior public research on that topic dates back to Oracle 11g (see also 3, 4, and 5), and I couldn’t find any information related to 26ai, so I decided to have a look myself.

According to the Oracle 26ai documentation, an auto-login wallet is protected by an obfuscated random password (see also 6):

An auto-login wallet is a read/write wallet that consists of both a PKCS #12 file called ewallet.p12 and a single sign-on (SSO) file called cwallet.sso. Both files contain the same content except that the ewallet.p12 is protected with a user password while cwallet.sso is protected with an obfuscated random password.

Keep in mind that auto-login wallets (SSO wallets) are different from local auto-login wallets (LSSO wallets): SSO wallets are portable across systems, whereas LSSO wallets are bound to the host on which they were created, preventing them from being used on other hosts. This is also why LSSO wallets cannot be used with RAC (see also 6).

Historically, LSSO wallets have used an additional obfuscation key derived from the username and hostname on which they were created, but this appears to have changed in 26ai as well, with the documentation stating that “local auto-login wallets are more secure now” (see also 7). In any case, the focus of this post is on SSO wallets, and I plan to cover the changes to LSSO wallets in Oracle 26ai in another post. That said, note that all findings in this post apply to Oracle version 23.26.0.

Auto-Login Wallet Obfuscation

When an auto-login wallet is created, Oracle 26ai generates a random 16-byte sequence from which it derives a password, along with a random 128-bit AES key used to obfuscate that password. The AES key and the resulting obfuscated password are both then stored in the header of the auto-login wallet file (cwallet.sso), followed by the PKCS#12 wallet contents (ewallet.p12), which are protected by the derived password.

The following steps describe the Oracle 26ai obfuscation process in detail:

  1. Generate a random 16-byte sequence (rand_seq).
  2. Transform each byte of rand_seq independently by applying a modulo-127 operation followed by a +1 increment. This maps each byte of rand_seq to a value in the 1–127 range, i.e. the 7-bit ASCII code range excluding NUL (0). The resulting byte sequence is used as the SSO wallet password:
  3. Generate a second random 16-byte sequence and use it as a 128-bit AES key (aes_key). The aes_key is stored at offset +13 (0xd) in the cwallet.sso file.
  4. Encrypt the password using aes_key and the following initialization vector: c0 34 d8 31 1c 02 ce f8 51 f0 14 4b 81 ed 4b f2. This initialization vector value is embedded and hard-coded in the Oracle binary in functions nzurcsh (encryption) and nzurcsc (decryption).
  5. Store the resulting 16-byte ciphertext at offset +29 (0x1d) in the cwallet.sso file. This is the obfuscated random password mentioned in the Oracle documentation.
  6. Read the original ewallet.p12 file, protect it with the randomly generated password, and write its contents to the cwallet.sso file starting at offset +45 (0x2d)

When Oracle reads the auto-login wallet at instance startup, it retrieves the aes_key and obfuscated password from the cwallet.sso header and then uses the aes_key to recover the original password, with which it subsequently decrypts the embedded ewallet.p12 contents and retrieves the master encryption key.

The first part of the bpftrace output in Listing 4 below shows that nzurrf_wf_31 calls nzty_random, which in turn calls the OpenSSL library function RAND_bytes_ex (see also 9) to generate a random 16-byte sequence (highlighted in green).

Each byte of the 16-byte random sequence is then mapped to the US 7-bit ASCII range (1–127) using the modulo-127 operation rand_seq[n] % 127 + 1. The resulting 16-byte sequence forms the auto-login wallet password (highlighted in green), which is then passed to nzurcsh through a pointer (buf=0x7ffdc63bb004).

Next, Oracle calls nzty_random_get and RAND_bytes_ex again to generate another random 16-byte sequence, which is stored in the buffer pointed to by buf (0x7ffdc63baef0). This byte sequence forms the 128-bit AES key (highlighted in blue) and corresponds to the 16-byte sequence visible in the cwallet.sso file at offsets 13–28 in Listing 3 above.

As its final step before returning, nzurrf_wf_31 calls into nzty_encrypt, which in turn calls into the OpenSSL low-level functions aesni_set_encrypt and aesni_cbc_encrypt (see also 10) to encrypt the randomly generated password (highlighted in green) with the randomly generated 128-bit AES key (highlighted in blue). Note that Oracle uses a fixed, hard-coded 16-byte initialization vector (IV), which is passed from nzty_encrypt to aesni_cbc_encrypt (highlighted in orange).

The aesni_cbc_encrypt function writes the resulting ciphertext representing the obfuscated auto-login wallet password to the buffer pointed to by the out argument (highlighted in red). This 16-byte ciphertext corresponds to the same 16-byte sequence visible in the cwallet.sso file at offsets 29–44 in Listing 3 above.

After obfuscating the auto-login password, the creation of a new auto-login wallet with the ADMINISTER KEY MANAGEMENT command shown in Listing 2 invokes the nzurrf_rf_31 function, which deobfuscates the randomly generated password.

Auto-Login Wallet Deobfuscation

This section walks through a practical test case illustrating how to deobfuscate the randomly generated SSO wallet password and extract the protected ewallet.p12 contents from the cwallet.sso file.

The test case demonstrates that anyone with access to the obfuscated cwallet.sso file can deobfuscate the wallet password and access the protected ewallet.p12 contents, which contain the TDE master key. Simply put, this means that anyone with access to the cwallet.sso file can decrypt the encrypted data in your database!

In summary, this section covers the following steps, which follow a similar approach to that described by Tjado Mäcke in 3.

  1. Extract the obfuscated random password from the cwallet.sso header and deobfuscate it.
  2. Extract the embedded ewallet.p12 contents from the cwallet.sso file and save them as a new PKCS#12 file.
  3. Open and read the extracted PKCS#12 file using the deobfuscated password.
  4. Change the password of the extracted PKCS#12 file.
  5. Replace the original ewallet.p12 file with the extracted PKCS#12 file to verify the deobfuscation and extraction process.

We first create a new encrypted tablespace and a test table in it. If we can access the data in that table after replacing the original ewallet.p12 file with the PKCS#12 file extracted from the cwallet.sso file, the test is successful. This post explained how Oracle 26ai protects auto-login wallets (cwallet.sso) with a randomly generated 16-byte password that is obfuscated using a random 128-bit AES key. Both the AES key and the obfuscated password are stored in the cwallet.sso file, followed by the original ewallet.p12 contents. If you lose your wallet but still have the corresponding cwallet.sso file, you can reconstruct the original ewallet.p12 file contents based on the process described above. The downside is that anyone with access to the cwallet.sso file can do the same. Therefore, access to this file should be protected very carefully.
